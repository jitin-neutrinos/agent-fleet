# Python → Rust porting (parity-gated)

## When to Use

- Porting a Python module/system to Rust with the Python original as the frozen, living spec.
- Continuing the Taal Hermes→Rust port (`~/Work/taal`) — the canonical instance on this machine. Before the first edit: load this skill and `rust-verification-harnesses`, run `~/.tool-router/route "<request>"`, and read `PROCESS.md`, `PORT-STATUS.md`, `HANDOFF.md`. Taal is hand-ported — do NOT start from `agentive-pipeline`; if a worker agent drafts a module, the brief and every acceptance gate are yours (see the standing rules).
- Reviewing or accepting any parity-gated cross-language port.

For rebuilding a Python system in Rust while the original stays the running reference (strangler-fig). A Claude-fleet copy of this skill serves Claude Code sessions; this one serves Hermes sessions.

## The loop (one reference file per cycle; small leaf files batch)

0. Find where it lands: read the last ledger rows' Rust-target column and the crate's `pub mod` list — a port goes beside its siblings, where the shared types already live. A new module in a thin early crate means re-declaring placeholder types, the first sign of a stub port.
1. Pick the next file in dependency order (leaf utilities first, entry points last). Read it COMPLETELY — every branch, threshold, counter, ladder — plus the area's AGENTS.md. Small leaf files (under ~150 lines each) batch into ONE cycle: one Rust module, one golden, one ledger row naming every file; god-files get a row per layer.
1b. **When a god-file must be split into layers, enumerate its methods with line spans FIRST and state the layer split as a count in the ledger row and the handoff header.** Split by dependency (pure/config/formatting → seam-driven cluster → orchestration), and make the LAST layer's row say how many methods remain unported — a row that reads "row N COMPLETE" for half a class is how the next session redoes or trusts banked work. A partial layer is its own row with its own commit, its own harness triplet and its own campaign gates; never fold a layer into the previous row's evidence.
2. Port it. Same semantics, Rust idioms. Keep every doc-comment's WHY. Carry invariants structurally where possible.
3. Gate it: unit tests PLUS a cross-language parity check PLUS one adversarial check nobody anticipated.
4. Check dependencies: every caller/callee, config/env/files it reads. Note wiring in the ledger.
5. Record a ledger row (file → target → state → exact evidence: command + output). Only then COMPLETE.

## Standing rules

- **The port itself is hand-ported; delegation is allowed for DRAFTING under your gates.** The owner revised the earlier blanket ban: a worker agent may write a module and its harness, but the PM (you) writes the brief, owns the oracle, re-runs EVERY gate on the worker's files yourself, audits against the reference, sends fix rounds, and does the integration (lib.rs, ledger, campaign). A worker's "done" is never evidence. **Decide delegation is not a speedup when the acceptance gates are the expensive part**: if writing the golden/runner/mutation-check costs more than the module itself, the worker's untested code arrives as a liability you must debug. Measure that on the first harvested module before delegating the next — in this project three workers were killed by a provider rate limit mid-task, and salvaging their output needed more PM work than porting solo.
- **A faithful port lands at 60–110% of the reference's line count** (tests included). Below ~40% = skipped semantics; reject and redo — apply this to your own work too.
- **Never accept "tests pass" as the gate.** Run the suite yourself, then add an adversarial input the author never wrote. When the reference ships its own tests for the module, replay them instead of hand-writing another golden — a pytest-tracing plugin turns that suite into replay rows, and the recipe lives in the `rust-verification-harnesses` skill under `reference-test-replay`. Six of this project's real bugs were found only by that replay, after the module's own parity suite had been green for sessions.
- **A green parity run is not a finished module — the mutation check decides that, and run it BEFORE declaring parity.** Proof: a module reached 305/305 scenarios green, then the mutation check caught only 15 of 29 targeted breaks, and every survivor was a branch no scenario reached. Refusing to call it done and adding the missing cases is the whole job: the golden grew to 347 scenarios and the module still has open diffs because coverage was the gap all along. The order matters: write the mutation list while reading the reference (each mutant is a branch to cover), and treat a survivor as "the golden is missing this scenario", never as "this rule is unreachable". A mutation check written after parity is green will find real gaps; one skipped entirely leaves them hidden.
- **When a test fails, re-read the reference source before touching port or test.** Wrong test expectations are as common as port bugs. Resolve against the reference with a live `python3` probe of the real module — never bend the port to a guessed expectation, never "fix" the test without checking.
- **Diff intermediate representations, not just outputs.** When values drift, dump the shape from BOTH sides programmatically and compare — never eyeball 200-char diffs in terminal output.
- **Corpus-audit hand-rolled parsers against the real data they will parse.** Synthetic fixtures reflect what the porter imagined; the live corpus has CRLF files, YAML block scalars, list-of-maps the fixtures never had.
- **Commit ledger/audit edits immediately after verifying** — a parity-cleanup checkout can silently wipe uncommitted ledger rows.
- **Drive the whole arc without pausing.** The owner wants arcs finished in one go — not re-sliced into ever-smaller sub-phases, and not a turn that ends on "want me to continue?". Batch small files per cycle, keep going through the arc's ledger rows, and stop early only on a real blocker, staged so a one-word reply unblocks it.
- **A layer is a COMMIT boundary, not a stopping point — and reporting "N of M methods ported" at the end of a turn is a failure to finish, not a status update.** Splitting a god-file into layers exists so each layer's gates stay cheap and its evidence is bankable; it is NOT permission to bank five layers and hand back a partial row. When the remaining work is one more layer of the same shape, keep going. The owner's standing objection to this project is exactly "if we keep converting phases into sub-phases we will never finish" — so a layer split must be derived from the reference's DEPENDENCY structure, never from session length, and the last layer of a row gets planned with the same seriousness as the first. Concretely: before starting a split, enumerate every method with its line span and state the FULL layer list up front; if the enumeration finishes and layers remain, the turn does not end until they are gated. If you must stop for a real blocker, the report leads with which layers are DONE, which are in flight, and that the row is not finished — never with a percentage that reads like progress.

## Parity harness

Triplet per module: `parity/gen_<area>_golden.py` (runs the REAL Python reference, writes golden.json) → `crates/<crate>/src/bin/<area>_parity_run.rs` (replays the same inputs, writes answers.json) → `parity/compare_<area>.py` (structural diff, exit 1 on failure). Name runners `<area>_parity_run` — two crates' binaries with the same name collide in target/release and the last build silently wins. Write and run the Python golden FIRST and read a sample of its rows (the raising and empty-input ones especially) before writing the runner: a driver bug found before the Rust side exists costs one edit; found after, it masquerades as a port diff.

**When re-running a gate by hand, copy the command out of the campaign script — do not reconstruct it.** A gate line names a runner binary AND a build-profile directory, and neither is derivable from the module name: two runners can serve one suite under different names (`<area>_parity_run` for the config schema, a differently-named one for the env ladder), and parity gates themselves may invoke `./target/mut/<runner>` (the fast mutation profile) while others use `./target/release/<runner>`. A hand-typed name that was never built fails as a comparator CRASH — a `KeyError` on the answers file's top-level key, or `MISSING-GOLDEN` rows — which reads exactly like a broken port while the actual cause is that no such binary ran. Triage rule: **a comparator traceback or MISSING-* row means the runner never wrote answers; fix the invocation, not the port.** Also confirm no mutation loop is running first (`ps -eo pid,cmd | grep mutation_check`) — invoking a runner while a loop is mid-flight measures whatever mutant is currently on disk.

## Verifying a parity claim (do this before saying "verified")

A green `compare_*.py` proves only that the committed `answers_*.json` still matches the committed `golden_*.json` — it says nothing about the current code. When asked whether a suite is verified (or before quoting a suite in a report), re-run BOTH sides in-session:

1. Move the stored answers aside, re-run the runner, then compare. A stale answers file from a previous session will happily compare clean against an unchanged golden.
2. **Check the runner actually loaded the artifact.** A runner that silently failed to load its model/checkpoint can leave the old answers file untouched, and the compare then passes on stale data. Read the runner's exit code and its output, not just the comparator's.
3. Parity runners commonly take model/fixture paths from env vars with defaults relative to their own crate dir (`TAAL_MODELS` defaulting to `../models`, `PARITY_DIR` to `../parity`). Invoking them from the repo root then fails on a path error that reads like a missing model. Pass absolute paths, or `cd` into the crate the defaults assume.
4. If the artifact is an exported model, confirm the golden was generated against the SAME export the runner loads (compare mtimes / record the export in the golden generator's docstring). A golden from an older export is a different spec.

5. **A parity run is only as wide as what it captures.** If the module's observable behaviour includes log records, guard-kwarg VALUES, or an ordered seam-call sequence, the comparator must diff those too — a return-value-only comparison hides every mutant that only changes them, which is how three survivors in one session survived six passes. Conversely, if the reference returns `None` from a side-effecting method, report the CALL LOG rather than inventing an outcome string on the runner side; the port may name its internal state for readability, and the runner must still emit the reference's shape.

Full command sequence, including how to tell a silent artifact-load failure from a real pass: `references/parity-verification-recipe.md`.

**Re-derive-never applies to the PORT too, not just the runner.** The golden is the spec; when a
survivor reveals your port invented a guard the reference never has, the fix is to REMOVE the port's
guard, not to explain it away. Three measured in one session: a per-platform restriction on shared
keys that the reference's own check can never fire (`only` holds enum MEMBERS, membership compares
against NAMES, so `plat not in only` is always false — the restriction is dead code upstream); a helper
signature whose second element the reference treats as a VALUE while the port read it as an
environment NAME; and a defaulting read where `getenv(name, default)` substitutes the default only
for an UNSET variable, so a set-but-empty variable returns "" — the port collapsed both to "empty
means default". **A port that "improves" on the reference is a port bug: an inert upstream check is
not an oversight to repair.** Confirm inertness by probing the real reference on an input that SHOULD
trip the guard and watching whether the code past it runs; then reproduce the inertness and write the
reason into the doc comment, so the next porter does not "fix" it either.

**An isolating scenario exists for any guard — find it by making the two branches DISAGREE.** The
recurring survivor is a scenario that passes through the guarded line without exercising the choice.
Four shapes that repeatedly worked, all found by asking the reference rather than by inspection: (a)
the guard is redundant against a sibling check — drop the sibling in the row so only the guard can
decide (seeding a second key the cleanup does not touch); (b) the guard compares against a constant
set — feed the row a value that is valid-but-different, or two valid values that the default would
collapse; (c) the row must feed a placeholder that FAILS the coercion the reference performs first
(`int(...)` rejects it, so the arm exits before the guarded line) — use an input that is both falsy
AND coercible, which in CPython is the STRING `"0"` rather than the int `0`; (d) the guard is a
container-membership test — Python's `key in "a string"` is a SUBSTRING test, so a row whose malformed
section is a string CONTAINING the key is the only shape that exposes a dropped isinstance check.

**The runner must be a mirror, never a second implementation.** Any answer the runner computes itself instead of calling the port's function hides every mutant inside that function. This bit twice in one session: a runner that re-derived a fallback-value expression, and a runner that logged a guard as kwarg NAMES while the golden recorded VALUES. When the two sides disagree on shape, the golden's shape wins — the port's internal representation is not the contract. The mirror rule also decides what to record when a helper yields several offsets: record the validator CALL LOG (which candidate was tried, in order, which won) rather than a value the runner would have to reconstruct — reconstruction is where a runner becomes a second implementation.

Treat a suite as "verified this session" only after all four hold. Otherwise say "green against stored artifacts, not re-run".

## Scripted-fake parity harness (both sides)

When the reference object is a heavy dependency (a DB, a service), drive it with a scripted fake: a list of outcomes popped per call. Port the FAKE as faithfully as the production code — three rules that each cost a debugging cycle when missed:

- **A fake that defines a method the REFERENCE also defines silently shadows it.** The highest-cost harness bug in this project: a `setattr`-loop or trait that copies host methods onto the reference mixin means the harness's own copy wins and the reference implementation NEVER RUNS — every scenario then passes for the wrong reason while looking perfectly green. It cost three separate debugging rounds (a sync/async mis-declaration, a hand-copied debounce method, a hand-copied capability probe). After wiring a host, assert the reference's own method is what answers (`mix.<method> is not host.<method>`), and delete any host method whose name the reference also defines. A shadowed method produces *identical* results on the happy path, so no diff ever surfaces it.
- **Check the reference's own sync/async signature before declaring the fake.** A `db = self._session_db` that the code then `await`s is usually an async FACADE over a synchronous store (`gateway/run.py` documents `_db` as "the raw SessionDB behind gateway._session_db (unwrapping the async facade)"). Declaring the fake async makes every `if not session_db` guard see a truthy coroutine, so the guards all pass and the real control flow is never exercised.
- **A class-level lookup needs a real subclass, not `__getattr__`.** `getattr(type(adapter), "_get_dm_topic_info", None)` resolves on the TYPE; a per-instance `__getattr__` cannot answer it, so the reference's own comment ("getattr() on a MagicMock auto-creates attributes, so every test double would match") only holds if the fake models the class lookup literally.
- **`__getattr__` fires only for MISSING attributes and must key on the EXACT probe name.** The reference reads `getattr(adapter, "_create_dm_topic", None)` — underscore-prefixed. A fake whose method is `create_dm_topic` answers that probe with None, and the whole method silently skips. Mirror each probe name exactly, and after wiring, assert the probe resolves on the fake you built.
- **A process-global logger accumulates handlers across scenarios.** A capture handler attached per scenario multiplies every log record by the number of scenarios run so far; attach ONE handler at import, set `propagate = False` (the reference emits through that logger directly), and clear the captured lines at the start of each scenario. Also exclude the fake's own `logger`/`logs` attributes from any attribute-copy loop, or records land in both sinks.
- **A fake must not re-emit what the reference logs itself.** If the reference calls `logger.info("rename: ...")`, the fake adapter answers the call only — appending the same line by hand doubles every record and makes a correct port look wrong.

- **Default-on-empty must match.** `step = script.pop(0) if script else "ok"` means an exhausted script succeeds silently; a Rust `remove(0)` or `drain(..1)` on an empty Vec panics instead. Guard with `if s.is_empty() { Ok } else { s.remove(0) }`.
- **Record the call BEFORE applying the scripted step.** Failed attempts must still appear in the recorded log — attempt-count parity (which catches loop-arm bugs) depends on counting raises as well as successes.
- **Shared mutable fakes need interior mutability.** The fake is cloned into `Arc<dyn Trait>` closures, so script/logs/maps are `Mutex<...>` (or atomics for flags), and `#[derive(Clone)]` comes off the struct. Variant fakes that override one method without popping the script (e.g. a rebuild that always succeeds) get an atomic flag, not a subclass.
- **When the port's constructor takes `Box<dyn Trait>` but tests hold `Arc<Fake>` to read counters afterward, add a blanket `impl<T: Trait + ?Sized> Trait for Arc<T>` forwarding to `(**self)`** in the port — then `Box::new(store.clone())` compiles and the original Arc keeps readable state. Without it every call site fights E0277.
- **Expose seed/introspection seams on the Rust port mirroring the Python tests' direct attribute writes** (`store._dirty_transcripts[k] = [...]`). Public `seed_pending`/`seed_failures`/`failure_count`/`pending_queue` methods keep the runner a 1:1 mirror of the golden's scenario setup; contorting scenarios through the public API instead drifts the setup and produces phantom diffs.
- **When the golden pins a module attribute (`mod.fn = fixed_table`), the port needs the same injection point** — a swappable fn field/typedef the runner sets, not a hardcoded call to the general helper — or the replay cannot mirror the pinned classifier and diverges on every row that exercises it.

## Golden-generator pitfalls (Python side)

- **Match evaluation order between golden and runner.** A Python dict literal printed as a block reflects state AFTER the surrounding statements — if the runner captures mid-sequence, rows disagree. Capture state at the same point on both sides.
- **Patch the name in the module the reference RESOLVES at call time, which is often not where it is defined.** An in-function `from X import f` binds `f` into the CALLING module, so rebinding `X.f` is invisible; the same for a name imported at the top of the module under test (`loop_heartbeat_forever` lives in the watchdog module but is reached through the module under test). Get this right by reading the reference's own import lines, not by assuming the definition site is the patch site. Symptom: the fake is installed, the scenario runs, and the patched function is provably never called.
- **A fake must return what the real API demands, or the harness measures the fake's shape.** `asyncio.create_task` rejects a plain object with TypeError, and a `_log_suppressed` around the call turns that into a spurious DEBUG plus skipped work downstream — the row then "passes" while proving nothing about the port. Same class: an `async def` fake called without `await` hands the reference a truthy coroutine; a fake returning a plain object where the reference expects an enum or a mapping misses every keyed lookup. When a golden row shows a suppression record you did not expect, suspect the fake's return type before the port.
- **A module-level `getattr(MOD, "NAME", None)` is not a host attribute — patch the MODULE or the row is a no-op.** The same shape as the `signal.SIGUSR2` and `getattr(type(x), …)` traps: a fake that only sets a host flag leaves the reference reading the real module global, so a "POSIX-only" row fires on a Windows-shaped input and the flag never mattered. Delete the module attribute for the row and restore it in the `finally`.
- **A `getattr(x, k)`-shaped option must be EXPRESSIBLE as ABSENT, and an explicit JSON `null` is not absent.** `spec.get(k)` in the Rust runner returns `Some(Value::Null)` for an explicit null, so a bare `.map()` manufactures the value and makes the "not configured" branch unreachable — the parity run is green and the branch is untested. Filter the null out, and when the reference distinguishes "attribute missing" from "attribute present and false", carry that as two separate spec fields (an absent task vs a finished task) instead of overloading one boolean.
- **An identity-bearing reference value must be recorded as a TOKEN, not a repr.** A golden that records `service` or `adapter` captures `<Foo object at 0x7f…>`, which no replay can reproduce and which hides the property you actually want to compare (its RUNNING status). Record the derived fact, and substitute machine-dependent paths and homes with `$HOME`-style tokens so the row is not pinned to one machine.
- **Re-binding a patched attribute must be restored in the same `finally`, and a module-global patch list is the usual leak.** Six rows of one suite showed the same `load_config` call because an earlier row's scope was still installed. Snapshot every patch target at the top of the row and restore all of them in one `finally`, including the ones the row did not itself install.
- **`json.dumps(..., default=str)` silently turns `None` into the STRING `"None"`** when you wrap nullable fields in `str(...)` for safety. Emit `x.isoformat() if x else None` — a string-typed None on one side can never equal real null from the other.
- **Record sorted lists, never set/frozenset reprs.** `sorted({...})` in the golden; a `"{'a', 'b'}"` string will never equal a JSON array.
- **Pin config defaults explicitly in fixtures** when the reference constructor applies environment-dependent defaults; otherwise golden and runner test different configs.
- **Import the reference with `sys.path.insert(0, 'hermes-ref')`** and silence expected stderr logging; a nonzero exit with a complete JSON file is still a good golden.
- **Pin heavy dependencies when driving a Python mixin in a golden** (`store._db = fake`). Unpinned, a property-style resolver can run the REAL acquisition path (opens a real sqlite, hits the network) and the scenario silently tests the wrong backend. Reach `@staticmethod` helpers on the class — rebinding them through an instance passes a spurious `self` and breaks parsing.
- **Build scenario names from an index and assert uniqueness in the generator's `main()`.** Names derived from truncated data (`name[:14]`) collide, and a results dict silently keeps only the last scenario — a whole case vanishes from the golden and nothing fails.
- **Give every golden scenario its own scratch dir (`tempfile.mkdtemp()`).** Two fakes pointed at one shared `/tmp/...` path leak rows between scenarios — an earlier scenario's writes surface as phantom keys in a later section's diff. Same for reference code that reads state files by direct path instead of an injectable: seed a real temp file per scenario and monkeypatch only the write side.
- **Deepcopy scenario specs before running, and serialize a pristine copy.** Scripted fakes POP from outcome lists stored in the spec, so serializing the same dict after the run records drained scripts and the replay runner silently tests defaults. Same aliasing bites any fake that mutates its input list.
- **Pin everything that enters the output bytes.** Random scratch roots embed into recorded file paths the replay side can never reproduce — use a fixed, wiped temp dir and substitute a token (`$SCRATCH`) in the golden; neutralize wall-clock stamps in side files (`marked_at` → constant). And re-seed per-scenario state files AFTER any wipe: a helper that unlinks the db inside the run loop erases the seeds you just planted.
- **A helper that returns `{}` vs `None` changes which branch runs.** `_error_obj(body)` returning an EMPTY DICT (not `None`) means the follow-on `body.get("message")` fallback fires for EVERY dict body — a port that models it as `Option::None` and gates the extraction on `Some` silently drops every flat-body message, so a 404 carrying `"not available on the free tier"` classifies as a bare "not found". Model empty-collection returns as empty collections, and read the fallback chain in the reference in order rather than assuming the guard means "skip".
- **A message-grammar helper is usually a TABLE of patterns, not one regex.** A helper the reference implements as four ordered patterns (a field-name variant, a "retry after Ns" form, a free-text "resets in 4hr 5min" form, a header lookup) ports correctly only if you transcribe all four plus their precedence — a port implementing just the first matches nothing on the other three, and the missing rows usually surface as a missing side-channel field rather than a wrong verdict. When a ported helper's tests fail on an absent optional field, count the reference's patterns before debugging the branch that sets it.
- **A port reading a header the reference deliberately ignores invents data.** `x-ratelimit-reset` is an epoch, not delta-seconds; the reference reads only `Retry-After`. Treating the extra header as seconds produces a plausible-looking reset window the reference never computes. When a test pins a field's ABSENCE, the port is reading something it shouldn't.
- **Convert JSON-round-tripped lists back to tuples before membership calls.** A reference signature taking a set of `(platform, profile)` tuples matches NOTHING against a list of lists, so fixtures pass while the production claim path never fires — `{tuple(t) for t in tgts}` at the driver boundary.
- **Parity "ok" probes through `from_dict`-style loaders need a FULL valid wire dict.** Reference loaders index required keys (`data["session_id"]`) and raise on a minimal dict, so `{"session_key": ...}` parses to None — an `ok: false` diff that looks like a parse bug is a fixture bug.
- **A generator's stdout must stay pure JSON.** The campaign pipes stdout straight into the golden file; a diagnostic `print()` or a second `print(json.dumps(...))` yields two concatenated objects and "Extra data" on parse. Route every diagnostic to stderr.
- **Can machine-dependent reads before generating.** Any reference path that reads `$HOME/.env` or live host state through a helper (a plugin `is_connected` reading `gateway.get_env_value`, a sessions-dir default) makes the golden a snapshot of THIS machine — a row silently passes because a real token sits in the user's `.env`. Patch the helper to a canned table inside the scenario and mirror it with an injectable seam in the port, so both sides answer from the same spec. Related: a gate that reads LIVE user state (a skill corpus, a config dir the user edits) goes stale when the user edits that state — a corpus diff naming a just-edited file is a stale fixture; regenerate it before debugging the port.
- **Scenario env patches must be applied AND restored by the runner, and recorded in the spec.** Env vars set for one scenario persist in a single runner process and poison later rows (a multiplex override set for an env row flipped every later config row's override arm). Spec carries `{var: value-or-null}`; the runner removes the var first, applies the patch, reads, then removes again.
- **A logger-scope mismatch shows up as EXTRA records, not wrong ones.** When the module under test logs to logger A but calls a sibling logging to logger B, the reference's capture handler only sees A — the runner must filter the port's records to the same scope (document which suite owns which logger), or every row crossing the boundary diffs spuriously. Give each handler its OWN buffer keyed by `record.name` and let each scenario drain only the loggers its own function reads: one shared buffer leaks a helper's DEBUG line (a sibling `resolve_turn_limit`) into an unrelated row.
- **A captured logger at the default level records NOTHING at INFO.** `logger.info(...)` is dropped when the logger's effective level is the default WARNING, so every info row silently captures an empty list and the port's record looks like a spurious extra. Set each captured logger to DEBUG explicitly.
- **Drain the capture buffer BEFORE each scenario, not only after.** A handler attached once and popped only by the reading scenario lets row N inherit row N-1's records on a logger it never touches — a row reading `raw=None` shows the previous row's `unparseable value 'abc'` line. A `clear_logs()` at the top of every scenario closes it; the symptom is a diff that MOVES when you reorder unrelated fixtures.
- **A scenario's stand-in object must carry every attribute the reference reads, including nested ones.** `getattr(cfg, "platforms", {})` on a stand-in with no `platforms` attribute silently takes the empty-dict default, so every violation row records `None` and the port's real answer looks like a spurious extra. Build the stand-in's children before the call, and keep one row where the reference demonstrably takes a non-default branch so the omission cannot hide.
- **An absent-int sentinel is a VALUE, not null.** A reference returning `-1` for "no position" must not be compared against the port's `None`; convert at the runner boundary and say which side the sentinel came from.
- **Match the generator's serialization quirks exactly.** Non-finite floats: Python's json writes `Infinity`/`NaN`, which serde_json REJECTS — emit Python `repr()` strings in the generator and normalize on the comparator. A generator that truncates captured messages (`m[:90]`) needs the comparator to truncate the port side identically. Log-record shape (dict `{"l","m"}` vs pair array) must match the golden's, not the runner's convenience. An empty `logs` list is the no-records case on both sides — drop the key before diffing instead of requiring both sides to emit it.

## Port pitfalls (Rust side)

- **A SUPPRESSED exception is usually still LOGGED — swallowing it silently makes the branch unobservable and its mutant unkillable.** `with _log_suppressed(DEBUG, "… %s", …):` discards the error but writes a record, and that record is the only observable proof the suppression arm ran. A port that models the suppression as `let _ = seam()?;` looks correct, kills nothing, and leaves the row with no way to distinguish "the guard fired" from "the guard was never reached". Record the swallowed error at the same level the reference logs it.
- **A typed Rust seam can make a reference TYPE GUARD unreachable, and the port then looks correct while testing nothing.** When the reference does `isinstance(resolved, str) and resolved.strip()`, a seam typed `Option<String>` forces the replay runner to hand the port a string — the runner stringifies the reference's Mock answer, the `isinstance` arm never fires, and a mutant on it survives. If the reference has an `isinstance` check on a value from a seam, that seam must carry the RAW wire value so the check is reachable from a scripted fixture.
- **Port the loop, not the intent.** When the reference builds a value inside a loop and uses it stale-by-one-iteration deliberately (converging marker widths), reproduce the loop exactly — "cleaning it up" to rebuild after the loop breaks byte-parity.
- **Trait `impl Future` is NOT `dyn`-safe.** A Rust trait returning `impl std::future::Future` cannot be made `Arc<dyn Trait>` — the compiler rejects with E0038 (not object-safe). When a ported async Python method needs a trait seam (e.g. compression-tip DB), either keep it synchronous (`fn ... -> Option<String>`) and manage `.await` at the call site through a future wrapper, or use `#[async_trait]` with an explicit dependency — never assume `impl Future` works behind a `dyn`. If a trait seam must stay object-safe, prefer a synchronous trait + an executor wrapper over `impl Future` return types.
- **Error-recovery success paths that `continue` bypass the termination checks of the plain success arm.** A reference retry branch (e.g. rebuild-index-then-retry) often ends `ack(); continue` WITHOUT the `if queue_empty: return` the main success arm has — so the loop top re-processes the same item once more. Model each arm as a distinct enum outcome (e.g. `Done` vs `FtsDone`) instead of funneling every success into one variant, and read the reference's control flow line-by-line to see which arm checks what. Symmetrically, **every `return` inside a retry loop — including give-up/drop paths — must run the same queue-ack/bookkeeping the success path runs**, or a poisoned head survives to block later writes. Both classes are invisible to unit tests and only surface as parity diffs on attempt-count fields (e.g. `appended: 3 != 2`); when attempt counts disagree, trace the reference loop arms before assuming the fake is wrong.
- **Identity-tracked loop variables map to capture-by-value + front-equality.** Where Python holds `msg = pending[0]` and later tests `pending[0] is msg`, clone the head at bind time and compare `pending.first() == Some(&msg)` at ack time — exact for a single-threaded drain, and the borrow checker will not let you hold a live reference anyway.
- **Port each mixin of a decomposed god-class as its own struct over a PROJECTION of the shared state object.** The Python mixin reads host attributes (`self._lock`, `self._lazy(...)`); the Rust port takes trait seams for the host's reach-throughs (db handle, save hooks, file writes) and models only the fields that mixin touches — fields owned by a not-yet-ported module stay opaque wire dicts (`Map<String, Value>`) that round-trip byte-stably. Injectable clocks (`now_epoch`/`epoch`/`uuid_hex`) replace module-level `datetime`/`time`/`uuid` monkeypatches. Modules that reach through a live `runner` or adapter (the gateway `run_*` phase files) follow the seam table in `references/runner-mixin-seams.md`.
- **Generate byte-pinned strings from the reference by script** (a generator that imports the reference and emits Rust consts via `json.dumps` escaping). Hand-transcription of 1,000+ char prompt/carrier strings drifts invisibly until a parity diff scrolls past it.
- **Every DEFAULT/TIMEOUT/THRESHOLD constant is a measurement, not a plausible number — and the ones that matter are load-bearing.** Intervals, cadences, strike counts and backoff figures are the timing a caller FEELS: a watchdog probed every 5s when the reference probes every 30s hides a frozen loop for a fifth of the intended time, and parity stays green because no row asserts on elapsed behaviour. Print the whole constant set from the live module in one probe before writing the Rust consts block, and give each a unit test asserting the measured value. Constants consumed elsewhere in the project are imported, never re-declared — a locally retyped copy drifts silently the moment the generator regenerates.
- **Python evaluates a call's ARGUMENTS before the call, so an argument with side effects is observable in the call log BEFORE the callee.** `faulthandler.enable(file=self._open_faulthandler_log())` opens the log first; modelling it as two independent calls in the other order produces a different trace while behaving identically. The same applies to `register(sig, file=self._open_…, chain=False)`. When an ordered seam log disagrees only on two adjacent entries, check argument-evaluation order before assuming a branch bug.
- **A NESTED suppression block does not log a second time.** `except: with _log_suppressed(MSG): try: … except: pass` logs once for the outer failure and once for a separate later block — the inner block's own failure is caught by the same `except`, so a port that re-logs per level invents a record the reference never emits. Count suppression blocks by reading the `try/except` nesting, not by counting operations; when a log-record diff is purely a repeat of one message, the repeat is the suspect.
- **`serde_json::json!` cannot hold statement blocks as values** — hoist computed values to `let` bindings before the macro. Large `json!` literals (~45+ entries) also hit the macro recursion limit; build a `Map` with an insert loop instead.
- **`.contains(&"str")` fails to compile on `Vec<String>`** — use `.iter().any(|t| t == "...")`.
- **Attribute/identity semantics map to `Arc::ptr_eq`** — where Python compares object identity (`is`) for CAS/restore paths, compare `Arc` pointers of the boxed closure/entry.
- **`is SENTINEL` on a module-level sentinel is IDENTITY, not text equality — give it a dedicated token type.** The trap is that the sentinel's rendered form is a perfectly ordinary string, so a port that compares text accepts a value that merely READS the same and wrongly takes the reference's identity-only branch (here: releasing a pre-claimed slot the reference leaves held). Serialise the real sentinel as a distinct token (e.g. a tagged object) so the two are apart by construction, and put a look-alike-string row in the golden — it is the only row that distinguishes identity from equality.
- **No `__globals__` introspection exists** — where Python derives ownership/caller module from a function object, Rust must take it as an explicit parameter; document the adaptation in the ledger row.
- **Python exceptions in handlers map to `std::panic::catch_unwind`** producing the same error envelope.
- **Regex crate has no lookahead** — patterns with `(?=...)`/`(?!...)` need a two-step equivalent (match-then-cut-at-boundary), never a rewrite of the pattern's intent. Recipe and trap list for the whole class: `references/regex-scanner-state-machines.md`.
- **A hand-rolled `finditer` scanner MUST advance past a REJECTED match, or it loops forever.** After a candidate fails the extension/boundary/validation test, set the cursor past the KEYWORD position — not past the match start, and not back to it. Python steps one character past a failed attempt and keeps scanning, so a rejected tag is genuinely followed by a matching one; a scanner that re-seeks from the same offset never terminates. Two distinct hang shapes seen in one module: re-seeking at the rejected match's start, and a token scan that read `chars[i..]` guarded only on whitespace, so a tag inside backticks scanned past its own closing fence. **A parity runner that hangs is nearly always a non-advancing cursor or a position mix-up, not a slow test** — bisect it (below) rather than raising timeouts.
- **Return a STRUCT from a "find the next keyword, plus the run before it" helper, and delete the tuple version.** A helper returning `(match_start, keyword_pos)` destructured as `let Some((kw_at, _))` hands the caller the match start, which silently rewinds the cursor by however long the leading quote run is — an infinite loop on exactly the inputs that have a quote or fence before the keyword, and the swap compiles clean. Ship `Match { start, kw }` so the type system blocks the mistake; leaving the tuple helper alongside it means the next call site picks the wrong one. Spell both names out at every call site even with the struct. This one shape produced THREE separate hangs (the swapped tuple, a rejected candidate re-found at its own start, and an unbounded `chars[i..]` token read) — a single scanner is worth auditing against all three.
- **Gate one thing per sitting, highest-certainty first: land the HARNESS fix before the port rewrite.** When a run leaves both an open parity diff and a suspect gate, fix the GATE first, alone, and confirm it can fail — a comparator/tamper defect silently invalidates every count you are about to argue about, and rewriting the port while it is deaf means you cannot tell your fixes from the harness's blindness. The reverse order is worse than either: a scanner rewrite plus a dozen new edge scenarios in one pass moves a green 539/0 to 71 diffs, and the regression is indistinguishable from the seven real bugs it also fixed. Sequence: (1) audit + fix the comparator and prove it detects tampering, (2) re-run the mutation gate and read the true survivor count, (3) only then add scenarios or rewrite the port, (4) land each surviving diff in its own small verified step. **The same rule governs a NEW layer: write the golden and runner for a layer and get them green against the UNCHANGED reference before porting anything into that layer.** A harness that has never produced a real diff has not been shown to produce one, so its green tells you nothing about the port — and a layer's first green run is the one moment a shape mismatch between golden and runner is cheapest to find.
- **Never reason a span boundary forward from the pattern text — measure all the candidate offsets and read which one the reference uses.** Regex-shaped helpers carry three different end offsets (capture-group, whole-match, and a post-hoc validated candidate) and the span boundary uses the third. Inferring which applies, then "correcting" the port to match the inference, produces a one-character over- or under-delete that passes every hand-written unit test and silently eats a space or a character in production. Two wrong inferences in a row is the normal cost; one measured probe printing all three numbers ends it. Recipe: `references/regex-scanner-state-machines.md` § "Three distinct end offsets".
- **When a port that copies a reference's CONSTANT TABLE verbatim still rejects every row, the table's internal convention is the bug.** The element format (dotted `'.png'` vs bare `'png'`, prefixed, already-lowercased) is invisible in a type signature and in most diffs, because a mismatched table rejects EVERY row at once — which reads as "the scanner is broken" and sends you into the wrong function. Print one element's `repr` from the live reference before writing the table, and check the comparison site strips nothing on either side. The same audit covers the slice that builds the lookup key: when the split index points at the character AFTER the delimiter, the key must start one earlier or it never matches.
- **Two similarly-named reference predicates are not interchangeable.** A regex-shaped `known_extension` stops at a lookahead terminator; a raw `Path(p).suffix` check does not. Aliasing the second to `!first` merges two different classifications and sends tags down the wrong branch. When a port ends up with two same-purpose-looking predicates, read each body and confirm they genuinely differ — or the "simplification" is the bug.
- **Python slice deletion with an inverted range is a NO-OP; Rust `drain` panics.** `del lst[3:1]` and `del lst[5:5]` delete nothing; `chars.drain(3..1)` panics on range end < start. Guard `if start >= end || start >= len { continue }` in any ported span-deletion loop, and put an inverted range in the golden — it is the row that catches the panic.
- **A reference helper's DOCSTRING routinely omits an arm its code has — read the body, not the summary.** The summary of a span-masking helper said "code, quotes, JSON string values"; the body also protected blockquotes, skipped a backtick span preceded by `MEDIA:` (a path quote, not code), and treated a validating whole-tag in inline code as a real directive. Port from the body, then diff your list of arms against the code line by line.
- **When a helper you expected to be module-level is an AttributeError at import, that IS the finding — the real location is a `@staticmethod` on the adapter class.** Golden generators surface this immediately (`AttributeError: module 'gateway.platforms.base' has no attribute '_mask_protected_spans'`); read the reference to find the true owner rather than adding a module-level alias.
- **A generated-from-the-interpreter artifact beats a hand-written expectation, and the disagreement is the finding.** When a table generated from CPython's `unicodedata` fails a test whose expected values were written by hand, check the interpreter before touching either: the hand-written range was the bug (ASCII punctuation is NOT the obvious symbol ranges — `$ < = > ^ ` | ~` are Sc/Sm/Sk). Report the divergence, delete the hand-written guess, and keep one answer path.
- **Do not hand-write an ASCII fast path next to a generated Unicode table.** The fast path is a second source of truth for the same predicate, and it will disagree on exactly the characters nobody thought about. Delete it and take every code point from the table; measure the cost before optimizing, not after.
- **Python `%r` in log messages is `repr`, not Rust `{:?}`.** `%r` of a string renders single quotes; of an int, bare digits. A port formatting with `{:?}` emits `"junk"` where the reference logs `'junk'` — every captured-record row diffs. Route `%r`-formatted values through a `py_repr_str` helper (strings only; non-strings render via `str()`).
- **Closures returning structs that borrow captured locals fail E0515** — restructure to a plain `fn` taking the borrowed params, or build the struct inline at each call site with `let`-bound closures.
- **`OnceLock` cannot be re-set** — test seams that need to swap an instance need a `Mutex<Option<...>>` or a dedicated test hook instead.
- **`[dev-dependencies]` do not reach `src/bin/` parity runners** — cargo links them only for tests/examples; a runner importing an integration crate (rusqlite, reqwest) needs it as a real dependency of that crate or the build fails on unresolved imports.
- **A closure borrowing from a struct that is also moved into a `Box<dyn Trait>` fails E0597** — share the state via an `Arc` cloned into both the db handle and the closure instead of borrowing from the local.
- **`fn`-pointer struct fields cannot capture per-instance state** — a predicate that varies per handle (e.g. `fronts_platform`) must be `Box<dyn Fn(&P) -> bool + Send + Sync>` or resolved at construction; an `fn` pointer silently makes every instance answer identically.
- **Check the workspace dependency direction before porting a module into a crate.** If the types a module needs already live in a crate that DEPENDS ON the crate you're writing into, importing them creates a cycle. Declare a local PROJECTIONAL type (the subset of fields the module actually reads), document in its doc comment that it duplicates the sibling's type, and record in the ledger row which later port will unify the two. Reaching for the sibling type first wastes a compile cycle and tempts a bad fix (adding a dev-dependency back-edge, or moving the module to a wrong crate mid-arc). When the unifying port lands, MIGRATE the projection's call sites in the same arc and re-gate every suite that used the stand-in — an unreplaced projection alongside the real type is silent drift the next porter builds on.
- **When a reference helper raises and the loaders do not catch it, port the raise as an error type, not a silent default.** Probe the real exception on the exact fixture and keep its class observable (e.g. `min() arg is an empty sequence` propagating out of an id-canonicaliser for inputs a regex rejects); folding it to a return value changes what callers see on hostile input.
- **Watch for placeholder corruption after long file writes** — generation glitches insert tokens like `PLACEHOLDER`, drop braces, or splice duplicated blocks mid-file. After any large generated write: `grep -n PLACEHOLDER <file>` and compile before continuing. For files over ~150 lines, write per-function chunks to scratch files ending in a `// __TAIL__` marker, then assemble with `sed -i 's|^// __TAIL__$||' <target> && cat <chunk> >> <target>`, verifying the chunk count and tail after each append — whole-file rewrites of big modules glitch roughly half the time; chunked assembly essentially never does. When a spliced edit does land wrong, fix by brace-matched line surgery (find fn start, track depth to its close, delete that span), not by string-replace that can match a stale duplicate.

## Python semantics that bite

- `json.dumps` default separators are `", "` / `": "` — hand-roll `py_json_dumps` (serde_json preserve_order) for anything byte-compared; `ensure_ascii=False` for strings.
- **The tree carries TWO byte forms of `json.dumps`** — default args (", "/": " separators, `ensure_ascii=True`, `\uXXXX` escapes incl. DEL and surrogate pairs) and the common `ensure_ascii=False` variant. Check which one each byte-compared call site emits before reusing a helper; a shared `py_json_dumps` gives false diffs on routing rows that persist the ASCII-default form.
- `str()`/`repr()` of containers differ from serde: keep a `py_repr`/`py_str` pair; `_str_arg` coerces non-str non-None via `str()`, not the default. `repr(float)` is shortest-round-trip digits with fixed notation only outside decimal-exponent < -4 or >= 16 (exponent two-plus digits, `.0` on integral values) — Rust's default `Display` diverges on both ends; port a `py_float_repr` when floats serialize.
- **Python truthiness: `""`, `[]`, `{}`, `0`, `None` are falsy** — model explicitly where the reference branches on `args.get(...)`.
- **`a or b or c` returns the first TRUTHY OPERAND, not `True`.** A port that returns a bool from a method the reference wrote as an `or` chain is a behaviour change no assertion catches: `assert!(f())` passes for both, but a caller inspecting the value sees `"0"` where the reference returned the string. Return the winning raw slot.
- **`x.get(k, default)` passes the value RAW — it does not coerce, and it does not apply the default to a present falsy value.** `cfg.get("group", True)` hands a list, `"no"`, or `0` straight to the consumer; a port that runs it through `bool()` or a typed field silently changes downstream behaviour (a truthy `"no"` becomes `false`, and the consumer builds a different key). The default is `KeyError`-shaped: MISSING key takes it, PRESENT value is honoured unchanged.
- **`%s` / f-string interpolation renders the RAW value, and a conditional expression guards only ITS OWN condition.** `source.chat_id if source else "unknown"` tests `source`, not `chat_id` — so a null `chat_id` renders as the string `None`. Substituting a fallback for the null case is a port "improvement" and a behaviour change; port the expression's own guard, nothing wider.
- **`float(x)`-style coercions: the TypeError path lands on the DEFAULT and downstream math still applies** — `delay(None)` is default+slack, not default. Port the coercion over the whole `Value` (numeric strings parse; falsy/junk raise → default), then run the same clamp/format on every path, not only the numeric one. Python ints are also UNBOUNDED: a 20-digit chat id parses positive while Rust `i64::parse` overflows to false — handle the overflow arm. The STRING grammar is CPython's, not Rust's `parse`: `int()`/`float()` accept every Unicode decimal digit and Unicode whitespace, allow `_` only between digits, and reject an embedded NUL — `str::parse` does none of that. Port the pipeline and prove it with a mutation-corpus golden (`references/python-stdlib-semantics.md`).
- **`Optional[str]` slots keep raw JSON values — do NOT type them `Option<String>`.** A loader reading `data.get(name)` (no coercion) keeps an int `user_id` as an int: it round-trips and re-saves as an int, and rewriting it to `"7"` silently mutates every legacy row on its next save. Wrap the raw `serde_json::Value` in a small `Txt`-style slot type exposing truthiness/`str()`/wire-json. The same rule covers defaulted reads: `data.get("scope_id", data.get("guild_id"))` — a PRESENT null wins over the fallback; only an absent key falls through. And `x or default` selects by truthiness over the RAW value, not string-ness — an int display_name passes through as an int. The rule extends to TYPED dataclass fields: Python dataclasses do not coerce, so an int-typed field assigned the YAML string `"5"` stays `"5"` and one assigned null stays null — a port that runs a raw slot through a coercion helper rewrites history on the next save. `name = data.get("name", "Home")` keeps a PRESENT null and defaults only when the KEY is absent.
- **A dict keyed on an Enum plus `platform == Platform.EMAIL`-style comparisons make raw STRING arguments silently inert.** `self.platforms.get("email")` misses an enum-keyed dict and `"email" == Platform.EMAIL` is False for a plain Enum — a caller passing the string gets the global default with no error. The port must model the two call forms distinctly (enum-resolved vs raw string); the parity rows that expose it pass the same value both ways and expect different answers.
- **serde_json models `bool` and `Number` as different variants — Python's `isinstance(x, int)` being true for bool must be handled explicitly.** A `Number` arm that doesn't exclude `Value::Bool` (or a Bool that falls into a generic truthy arm) classifies `True` as the integer 1 where the reference's `isinstance(x, int) and not isinstance(x, bool)` deliberately excludes it; the reverse (treating a bool id as a str-able scalar) turns a reference raise into a match.
- **DB row order flows into the port's in-memory map and is observable** — when the reference loads a dict from an unordered query and callers see first-match lookups, tie-broken sorts, or file key order, that insertion order is contract: a `BTreeMap` (or any sorted map) silently re-sorts it and produces diffs only in order-sensitive scenarios. Use an insertion-ordered map (`indexmap`) for both the in-memory map and the persistence trait's rows type.
- **Optional fields are OMITTED, not null-written, in reference serialization.** Dataclass `to_dict()` methods commonly write optional keys only when truthy (`if self.x: result["x"] = ...`), so the wire shape drops unset optionals entirely — a Rust builder emitting `Value::Null` for them shows up as rust-only keys in every parity diff. Mirror omit-when-unset exactly; round-trip stability with the real data files depends on it.
- **Inventory every datetime field's clock AND timezone before porting to epoch f64.** One Python module routinely mixes THREE renderings: naive local `datetime.now().isoformat()` (no offset), aware UTC `.isoformat()` (`+00:00`), and `str(datetime)` (space separator); and one function may read BOTH `_now()` (local wall) and `time.time()` (epoch) as DIFFERENT clocks — a field persisted "now" from one must not be filled from the other. Port each as a separate epoch value + its own renderer (`iso_naive_offset` / `iso_aware_utc` / `str_datetime`), and let parity on the persisted-bytes prove which renderer each field uses — the diff `T06:20:00+00:00 != T06:20:00` is exactly this bug.
- **Hand-rolled civil-date math (days→Y/M/D, Hinnant algorithm) gets leap-day and year-boundary unit tests**, because every normal date works and only 02-29 and 12-31→01-01 expose off-by-ones in the era arithmetic.
- **Verify hand-computed epoch constants with a live `python3 -c 'datetime.fromtimestamp(...)'` probe before driving a golden** — a constant off by one day shifts every timestamp field in the answers file and the diff looks like a renderer bug.
- **`datetime.fromisoformat` must be ported from the C implementation, not the pure-Python one** — production runs `Modules/_datetimemodule.c`, and the two differ on edge strings (ISO week dates, one-digit offsets, `Z`, comma fractions, 7+-digit truncation, zero-offset microseconds dropped as UTC). Fetch the C file for the pinned version and port statement-by-statement; the pure-Python `_parse_isoformat_*` helpers accept a different language. Verify with a fuzzed corpus (thousands of seeded mutations of valid strings) plus `fromtimestamp` rows — and pin BOTH sides to a fixed-offset zone like `Etc/GMT-5`: named zones carry LMT history (a +05:30 golden diverges from any clean offset port pre-1900). Expect the year-1 fold probe (results within 24h of 0001-01-01 raise ValueError) and half-even microsecond rounding as separate rows.
- **`Path.resolve()`/`os.path.realpath` is not a component walk, and `Path` keys normalise.** `..` pops the already-resolved prefix (symlinks substituted), a symlink loop returns the unresolved remainder, and the result never keeps a leading `//`; as a dict/dedupe key a `Path` drops empty and `.` components and keeps exactly two leading slashes as a distinct root. Port `posixpath._joinrealpath` and normalise path keys the same way (`references/python-stdlib-semantics.md`).

## Verification and audit discipline (durable rules — session-verified)

- **Replay the reference's own fixtures before inventing synthetic goldens.** A replay uses `tests/gateway/test_*.py` fixtures (real `GatewayRunner` mocks with adapter state, `MessageEvent`, monkeypatched internals) rather than imagined scenarios; synthetic fixtures encode what the porter imagined the input looks like and miss branches the real fixtures reach. Load fixtures via `sys.path.insert(0, 'hermes-ref')` and consume them through a `S(name, **spec)` driver shared by both sides; compare result + ordered host-call log + captured log records. A replay that only runs the fixture's happy path is not enough — add hostile inputs (empty script, falsy raw values, missing adapter attributes, non-attribute `getattr` targets) to prove each branch.
- **Run the mutation loop in a BACKGROUND terminal, and never touch its files while it runs.** The loop snapshots each mutated source file and restores it in a `finally`, so any edit you make while it runs is silently reverted — a `git stash` taken mid-run captures a HALF-RESTORED file containing a live mutant, and appending a `#[cfg(test)] mod tests;` block gets eaten. Symptom to recognise: an anchor reported as "not unique" (that's a stranded mutant, not a bad anchor). Sequence it: mutation gate first, then edits, then re-verify parity. Each mutant forces a full crate rebuild, so a 40-mutant gate is tens of minutes and a foreground tool timeout kills it mid-run; launch through the terminal tool's background mode (a foreground call with shell-level wrappers — nohup/disown/& — is refused by the harness) and poll the log file.
- **After ANY mutation run, rebuild before reading parity.** The runner binary on disk is the LAST mutant's build; a stale binary produces a diff identical to the surviving mutant's, which reads like a port bug.
- **Never touch a source file a mutation gate is mutating.** Beyond the stash trap (SKILL.md),
  a snapshot test / rerun taken while the gate's breakage phase is live measures sabotaged code:
  session 11 read `WORKSPACE: 740 / 1` from a background alarm while `py_charclass.rs` carried
  the forced-final-sigma mutant; the same clean tree was 763/0. Before acting on ANY in-flight
  result, `git status --short -- crates/` and check the file against the mutation list — a
  failure during the campaign is the gate working, not a defect. Re-run on the restored tree.
- **Classify EQUIVALENT mutants AT SURVIVE TIME inside the checker loop.** The run_topics L1
  checker classified equivalents in a post-hoc pass over the printed summary; until that moved
  into the moment a mutant survives, the gate kept flagging two proven equivalents as survivors
  (Fix: `classified` list populated where SURVIVED is appended; summary prints
  `N killed, M documented equivalent, 0 survived`). Rows 70+ checkers inherit this shape.
- **A mutant that makes the runner exit non-zero is a KILL, not a survivor.** The golden requires those scenarios to SUCCEED, so a port that cannot produce the answer at all has broken the behaviour. Counting it as a survivor hides a real mutant.
- **A survivor is nearly always a scenario that never REACHES the line.** Before assuming a weak port, ask what input makes the reference actually execute the guarded line — then probe the real reference to confirm. Recurring shapes, all measured in this project: (a) a placeholder id where the reference does `int(...)` first, so a non-numeric value raises and exits BEFORE the line under test; (b) seeding only the row a cleanup path CLEARS, making cleared and never-cleared identical (seed a second unrelated key alongside); (c) recording that an action happened but not the VALUES of its guard kwargs; (d) not comparing LOG records, when the module's observable behaviour lives in `logger.info`/`warning` lines; (e) a predicate keyed on an internal marker no fixture sets — read the reference's own predicate to find the real key instead of probing plausible names.
- **Check whether the shape ALREADY EXISTS before adding a scenario for a survivor.** A survivor is normally a coverage gap, but it can also be an equivalent whose shape you have already covered — search the golden for the input class first (`any(shape in json.dumps(spec) for spec in golden)`) and, if it is present, you are looking at an equivalent, not a gap. Two more survivors are equivalent when a SIBLING check already converges on the same value: a second trim on an offset the primary scan already cut, or a guard that a preceding guard makes unreachable (`..` is rejected by the empty-suffix check before the all-dots check can fire). Prove the convergence against the reference, then classify — do not add a redundant row.
- **Audit the comparator's ARGUMENT HANDLING before trusting ANY killed/survived count.** A comparator that reads a fixed path instead of the answers path passed on argv makes every mutant compare against the GOOD answers file — so every mutant "survives" regardless of how badly it breaks the port. The signature is right and the output looks normal; only the count is wrong. Two defences: argv must WIN over any env-var default (positional args are the contract), and tamper-test the comparator once — corrupt one field in the answers file and require a nonzero exit. A mutation gate that has never been tamper-tested is a gate whose numbers are unverified.
- **A mutant that provably changes nothing is a BROKEN mutant — remove it, don't report it.** Replacing `None` with an empty value changes nothing when the very next probe refuses the empty value the same way. A check that cannot fail is not a check; keeping it in the denominator trains you to ignore survivor lists. **A mutant can also be structurally unfailable while looking real: replacing a match arm's BODY with an empty block keeps the arm matching, so it does exactly what the original did.** If a survivor's replacement removes work the arm used to do, check whether the arm still consumes its input — an arm that matches and discards is the no-op. The fix is to remove or rename the arm so control genuinely falls through, not to empty it.
- **A mutant aimed at a value NOTHING READS is unkillable by construction — point it at the decision instead.** A helper that returns a summary of what it saw, while the golden compares an effect the fake recorded, gives a mutant that mutates the summary a clean bill of health. When a survivor's target has no reader, grep for who consumes it and move the mutant one level down to the CONDITION that produced it. This is the same discipline as "a survivor is a scenario that never reaches the line", applied to the mutation rather than the golden.
- **A STUB in the port that always succeeds is a fake kill.** A helper whose body returns a fixed value kills every mutant aimed at the branch it replaces, because the branch is never exercised — and the project's own first-port rejection rule applies here: a compiling placeholder reads as finished work. Model the branch as an injected seam the runner scripts (so both the success and the failure arm are reachable), and grep the new module for `-> … { Ok(…) }` bodies that ignore their inputs before gating it.
- **A mutant reported SURVIVED may be a build failure you never saw.** The compile check must inspect BOTH stdout and stderr for `error[E` (or the exit code) — a failed build prints errors on stderr while a `tail -1` of stdout shows the last warning line, so the loop replays a stale binary and records a false survivor. Five of one pass's "survivors" were compile failures; fixing the detection converted them to kills or real fixture gaps.
- **Equivalent-by-construction is a third mutant class, beside killed and fixture-gap.** Two recurring shapes: (a) a bypass guard whose generic arm calls the SAME checker — skipping the dedicated branch changes nothing because the checker table answers identically; only a row where the two arms DISAGREE (token set, dedicated-checker prerequisite missing) kills it; (b) a normalize/validation arm that can never fire because a sibling guard pre-filters its only failure input (an empty name is rejected before normalize runs). When the reference's own structure makes the two forms converge, document the equivalence with the converging-path proof instead of hunting a scenario that does not exist.
- **A "documented equivalent" needs a structural proof, not a plausible argument.** Two forms are valid: an exhaustive sweep of the input domain showing 0 divergences, or a proof that the guarded state is UNREACHABLE at that point (e.g. a lane's entry condition already requires the value the guard checks, so the guard can never find it missing). Confirm unreachability by running the real reference with an input that *should* reach the guard and watching whether the code past it executes.
- **Distinguish "equivalent" from "unobservable" before classifying.** A mutant that cannot be killed because the golden never captures the channel it writes to is a fixture gap, full stop. Only a mutant that is genuinely unobservable *in the reference itself* is an equivalent.
- **Audit the checker before trusting a mutation "killed" count.** A comparator that slices the sorted diff to its first 12 entries before comparing passes a mutant with 55 extra mappings silently; a runner that re-derives `ratio` privately instead of calling the port's public `ratio_str` makes every mutant inside that function invisible; a golden written from the same wrong reading as the port has no teeth (the 12,895-pair difflib golden killed zero of the 21 mutants when the worker's port was wrong, because the golden encoded the same wrong `bpopular`-as-junk reading). Read the mutation log line by line; classify survivors as either "add scenario to golden" or "documented equivalent with measurement" (replay over the full golden or >=300k random pairs, record "0 differences"); never classify by argument alone.
- **Confirm workspace gate results by reading the final line for non-zero counts, not just the comparator's exit 0.** A `test result: ok.` with `0 passed; 0 failed; 0 measured` means the binary did not load (empty `test` filter or missing binary); a real gate shows non-zero passed/failed/ignored. Before reporting any suite, re-run both sides in-session, read `target/release/<runner>` exit codes, compare mtimes of exported artifacts with the golden's docstring, and state whether it is "verified this session" or "green against stored artifacts, not re-run". Never quote a broken aggregate (`0.00` cost / `0` output tokens) — quote per-harness rows.
- **Scripted-fake contract: default-on-empty must match on both sides** (`if s.is_empty(): Ok` not `remove(0)` that panics); **record the host call BEFORE applying the scripted step** so attempt-count parity holds (failed attempts must appear in the ordered log); **every `return` inside a retry loop** (including drop/give-up paths) must run the same queue-ack/bookkeeping as the success arm or a poisoned head survives; **shared mutable fakes need `Arc<Mutex<...>>` with `#[derive(Clone)]`** (not subclass variants); **inject seams for pinned module attributes** (`swappable fn` field / typedef) or replay cannot mirror them; **model empty-collection returns (`{}` vs `None`) exactly as collections** (not `None`) since `body.get()` on `{}` hits the fallback; **use insertion-ordered `IndexMap`** for persistence and in-memory maps so DB insertion order flows into the wire shape; **generate byte-pinned strings programmatically** (`json.dumps` escaping) never by hand-transcription; **pin everything in output bytes** (fixed scratch dir, substitutable `$SCRATCH` token, constant `marked_at` stamps, re-seeded state files after any wipe).
- **Rust std Unicode is NOT CPython's.** `char::to_lowercase` tracks Unicode 17.0; CPython 3.11 `unicodedata` tracks 14.0.0 — 55 extra lowercase mappings. For `str.lower`, `re` `\w`/`\s`, and `repr`, generate pinned tables from the reference interpreter (`parity/gen_*_consts.py`), sweep all 1,114,112 code points plus context strings, and treat any std char-class call in a stdlib port as suspect until swept. Confirm divergence by replaying a long-English-like corpus (>=200 chars with frequent-letter pairs) where the difference in `SequenceMatcher` block sizes surfaces; a short synthetic pair misses it.
- **Communication and output format preference (user mandate).** Answer in compressed, plain-English terms (caveman): no filler, no restatement of the request, no filler praise, no adjectives substituting for claims. Non-technical explanations use everyday analogies (streaming = radio switch, token tracker = fuel gauge, compression = packing clothes into a smaller suitcase, mutation audit = inspecting the inspector). Technical detail (flags, ports, file paths, command outputs) stays in file artifacts, not spoken. Default to `astra-canvas` cards (`kpi`, `table`, `steps`, `callout`, `compare`, `progress`, `timeline`, `checklist`) for any structured result — never prose tables or raw JSON blocks in chat. Code sections must be copyable (fenced blocks with a copy button in the UI); message composer height must grow dynamically; input composer sits above navbar with no top padding. Multi-device concurrent chat (same account, different tabs + across devices) and background agent status UI (`/bg` shows live work; `/bg` and `/steer` executed in parallel) are standing requirements, not optional embellishments.
- **Concurrent parallel commands.** Execute `/bg` and `/steer` in parallel, never sequentially; `/bg` must render a visible UI showing the background work (live status, phase, output snippet). Never run the `desktop` profile with `--yolo`. Never hand-install or replace NVIDIA driver / Mesa / Proton / Wine / ffmpeg / kernel (Nobara ships patched forks). Never touch `/run/media/notjitin/` (dual-boot NTFS) or `/boot/efi`. Full system updates go through `nobara-sync`; package management is `dnf5`, never bare `apt`/`pacman`/`pip` outside a container. Project dependencies belong in containers (`terminal.backend: docker`); host administration only through the `ops` profile, which asks first for anything destructive.
- **Evidence discipline.** Every non-trivial claim behind non-trivial logic must have a runnable self-check behind it (`assert`-based or a small test file). Report with the actual command and its actual output — never report a step as verified when it was not run. Before any irreversible host change (disk writes outside scratch, `rm -rf` outside scratch, package removal, driver/kernel change, destructive docker operation), stop, state exactly what will change in plain English, and wait for explicit confirmation. Never present a fabricated or synthetic result as real execution output.

## Mutation-loop cost: why a gate takes an hour, and what does NOT fix it

When a user asks whether the suite is stuck, establish the split before optimising anything. Measure one rebuild and one check:

```bash
touch crates/<crate>/src/<mutated_file>.rs
time cargo build --release -p <crate> --bin <runner>   # seconds
time (./target/release/<runner> parity/golden_<area>.json > /dev/null \
       && python3 parity/compare_<area>.py > /dev/null) # milliseconds
```

In this project the check is ~20 ms and the rebuild is ~15 s, so a 58-mutant gate is ~15 minutes of pure compiling and a 12-gate campaign is ~100 minutes. That ratio is the explanation to give; a slow gate is working, not hung. Prove it is progressing by the gate count climbing in the log, and by `ps` showing exactly ONE mutation loop.

Options measured and rejected — do not re-run these experiments:
- **`codegen-units` raised above 1** — 21 s → 12 s but only on a COLD build; warm rebuilds barely move because the cost is the final link, not the compiling.
- **`lto = false`** — cold build got ~2.5x WORSE; warm saved ~4 s. Not worth touching the optimisation that makes the shipped binary fast.
- **Per-gate `CARGO_TARGET_DIR`** — 41 s cold every time; loses more than it gains.
- **Running gates concurrently** — they share one target dir and mutate the same source files, so two would collide. Unsafe by construction.

**ADOPTED (owner-approved): a dedicated `[profile.mut]` build profile (inherits dev, `debug = 0`) used ONLY by mutation checks and their runners.** Measured: 0.7–0.8 s per mutant rebuild vs 13.3–14.1 s under release — a 33-mutant loop drops from ~7 min to ~40 s. Before trusting it, verify the mut-profile runner's answers are BYTE-IDENTICAL to the release runner's on an unchanged golden (done for three runners including a SQL-backed one; overflow panics in dev builds only help kill mutants). Release stays for arc-final campaigns and shipped binaries. Mutation checkers build with `cargo build -p <crate> --profile mut --bin <runner>` and run `target/mut/<runner>`.

**Phased campaign (adopted in the same pass).** Mutation gates are module-LOCAL — each replays only its own module's golden against its own mutants and cross-validates nothing else. Operating mode: per row, run the cheap suite plus ONLY that row's mutation gate; run the full every-gate campaign once at arc close. Implemented as `TAAL_FULL=1 parity/run_campaign.sh` (arc mode) vs the default per-row mode with `TAAL_ROW_GATE=<name>` selecting the row's own gate — measured 139.5 s per-row vs ~2.3 h full. The row is still UNGATED until its own mutation check passes; arc close re-proves everything at once.

## Never edit, stash, or test the tree while a campaign is running

The campaign and the mutation loops mutate real source files with a snapshot-and-restore. Two consequences a session hit live:
- A `cargo test` run during a campaign reads deliberately-broken code and reports it as a failing test. Confirm by checking `git status` for a mutated file and reading the diff before believing the failure; re-verify on the restored tree before quoting any count.
- A background job that reports a test count taken mid-campaign is measuring a mutant, not the port. Quote the campaign's own `TESTS passed=N failed=M` line or re-run after it exits.

## First-run diff triage

An initial parity diff list mixes two kinds: real port bugs and output-shape drift (golden emits `{sid: len}` maps, runner emitted a bare int; golden lists a field the runner named differently). Triage in this order:
0. Machine-path and host-state leaks first: an absolute path (`/home/...`) or a value that could come from this machine's `.env` means the GOLDEN is machine-dependent — token-substitute the path and can the env read before debugging the port at all.
1. `type X != Y` diffs on container fields are usually shape drift — fix the runner to emit the golden's exact container shape (skip empty entries the way the Python `dict` comprehension did).
2. Value diffs on attempt counts / orderings are usually REAL control-flow bugs — trace the reference loop arms before touching the runner.
3. **A diff that is byte-identical across an edit which should have changed it means you are reading a STALE BINARY, not a stubborn port.** `stat -c %y` the source file and the runner binary; when they disagree, `touch` the source and rebuild. This bites hardest when you edit the library and run a thin probe binary — `Finished in 0.05s` says nothing about whether the binary you are executing contains your edit. Two rounds of "fixing" a port that was never rebuilt is the cost; check mtimes first when a fix produces no change at all.
4. **Port bugs and GOLDEN bugs both show as diffs — decide which side is wrong before editing either.** Generator-side defects (unlowered logger level, undrained buffer, stand-in missing an attribute, an unreachable helper left as a module-level alias) produce the same symmetric diff list as real port defects. Triage by asking which side the evidence comes from: probe the reference directly for the expected value; if the reference agrees with the PORT, the golden is the bug.
5. Re-run after each fix cluster; the real-bug count on the first run of a stateful module is typically 1–3 even when 20+ diffs are listed.

## Reporting status on demand

When asked what's done / what's pending / whether the docs are current, answer from `git log` + the ledger, not from recollection of the conversation: read the last commits and the last ledger rows, check `git status` for uncommitted artifacts, and verify the HANDOFF header's row/test/suite numbers match the ledger before restating them.

**Check that each claimed evidence number is actually produced by COMMITTED harness code.** Re-run the gate from the committed tree and compare its scenario count against the number in the ledger row. A count that only holds when uncommitted generator edits are present is UNBANKED evidence, whatever the row claims — name it as such and bank the generator in the next commit rather than letting the row stand on a fixture that exists only in one worker's tree. Diff every modified golden in `git status` before treating it as semantic: a regenerated golden whose only differences are uuid-shaped temp filenames is regeneration noise AND proof the generator lacks the `$TMP`-token substitution the pin-everything rule requires — fix the generator, do not chase the port.

When the report opens the next arc, quote the next module's real shape read off disk (reference line count, method count, which sibling seam its host trait follows), and state the split you intend if the module is too large for one pass. A plan card whose numbers came from the handoff doc rather than the file is a card that can be wrong in the same direction the previous session was wrong. When the question is "have we STARTED the next thing?", the distinguishing evidence is a commit and a file on disk — not that you read the module. Say which of the two it is, in the first sentence. If a port is verified but not yet committed, say so and commit it (ledger row + HANDOFF) as part of answering — a verified-but-uncommitted row is pending work, not done work. Close with the concrete next module from the arc plan, not a generic "want me to continue?".

**Refresh the handoff doc in the SAME commit that banks the row — a stale handoff is the most expensive debt in this project.** The ledger row can be committed while the handoff's current-state block still names the row range, test count, gate count, and next module from several sessions ago; the next session then reads that pointer and redoes banked work. Treat the doc refresh as part of "the row is done", not a later chore:

- header line: row range, test count, gate/comparator count, and the commit they were measured at;
- the arc table: banked rows with per-suite evidence, PLUS a separate row for anything in flight marked UNGATED so a drafted module is never read as finished;
- an explicit note when the full campaign has not run end-to-end since the last commit (gates that passed individually are not an end-to-end run);
- "what's next": the concrete next module and its cycle, never the arc name the work started at;
- any doc quoting a superseded number gets a one-line `SUPERSEDED` banner pointing at the live one — leave the body as history rather than editing numbers that were true when written;
- a per-commit audit table so the trail survives, not just the current state.

Verify the refresh mechanically instead of by eye, quoting each number from a real log:

```bash
grep -c '706' HANDOFF.md                   # new count present
grep -cE '1–58|653/0|39 gates' HANDOFF.md  # stale current-state claims: 0
git log --format='%h %s' -N                # every new commit has an audit row
```

A number appearing inside a historical audit row is CORRECT and stays — rewrite only current-state claims. When asked "did you update all the docs", answer per file with what it claimed versus what is true; never treat the ledger row as if it implied the handoff.

**Never let reconnaissance read as progress in a status card.** Reading the next module, listing
its functions, or reporting its line count is NOT starting it — and a card that leads with "next:
row N" implies work exists that does not. The owner asked twice in one session whether the next arc
had actually started, because a reading had been described as a start. State the literal position:
the commit hash, what is on disk, and what the next piece of WRITING is. If a module is drafted but
ungated, say "DRAFTED, UNGATED" on the card, not in a paragraph further down. A check that has not
been written is not a formality to be promised later — it is the gate that decides the row, and on
every row in this project it found real defects.

**Status reports during a long arc: separate DONE-and-verified from IN-PROGRESS, always.**
The owner asks mid-arc and needs to know what is banked versus what is in flight. Lead
with the committed, gate-verified work and its numbers; then name the unfinished piece
and say plainly it is not counted; then the remaining size. Never let a module that
reaches parity but fails its mutation check drift toward "done" in the prose — it is
the single most likely thing to mislead, because a green compare feels finished.

State the session's remaining work as a short numbered list, written where the next
session will find it (a status file under `scratch/`), so stopping costs nothing. Say
what is NOT done in the same breath as what is. Where a task would take many
sessions, say that plainly instead of implying it is nearly finished — the owner
decides what to cut based on that number.

## Acceptance per file

Workspace tests green + parity suite green + clippy 0 errors + slop-detector clean + ledger row with the exact command outputs. Quote per-harness rows, never an aggregate that is known-broken.

**"Parity green" is provisional until the mutation check says so.** A module that matches on every scenario can still be missing the success arm, the timeout arm, or the sleep timings entirely. The mutation check is the gate that measures the SUITE rather than the port; run it before reporting a module complete, and do not report partial module state as a win.

- Until all of that exists the module is DRAFTED, UNGATED — say exactly that, never "done" — and run `done_gate(claims, evidence)` with the real command outputs before any completion claim; it rates compile-only evidence `partial`.
