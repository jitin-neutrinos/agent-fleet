## Private vault (gocryptfs) — operational reference

Layout: cipher `/mnt/hdd-storage/.vdloader-private-crypt`, mountpoint `/mnt/hdd-storage/video-download/private` (inside the media sandbox root). All vault state changes go through `~/.config/vdloader/private-vault.sh` (`vd-private` symlink in `~/.local/bin`; desktop entries `vdloader-unlock-private`/`vdloader-lock-private`). The unlock script prompts via kdialog when no password is passed as `$2` — for scripted/unattended runs pass the password as the second argument, never via interactive TTY.

## Multi-surface unlock-chain bugs (grep targets before editing)
Surfaces route through shared spawn points; a fix applied at one spawn site silently misses the others. Before changing unlock/lock/verify behavior, grep ALL spawn sites and patch each: `unlock` route uses `spawnSync('/usr/bin/gocryptfs', ...)` twice (mount + verify path), and `private-vault.sh` spawns gocryptfs/fusermount3 separately. Symptom of a missed site: one surface's unlock still misreports 'wrong password' (rc≠0 from `Invalid mountpoint: not empty` when the other surface holds the mount).

## Surface lease model (navigate-away primary, 2026-09-15)
- gocryptfs permits ONE mount per cipher, so web/desktop separation lives at the ACCESS layer: independent leases in `/run/user/1000/vdloader/vault-leases/{web,desktop}` (file content = epoch timestamp, mtime also read by lib/private-vault.ts). When navigating a shell into the mount for checks, `cd` OUT before asserting lock state — a shell whose cwd sits inside the mount keeps refs > 0 and blocks every unmount assertion.
- Commands: `unlock <web|desktop> [pw]` (mounts on first lease + writes that surface's lease), `lock <surface>` (removes it; unmounts only when NO live leases remain), `lock-all`, `heartbeat <surface>` (refreshes a LIVE lease — an expired lease can NEVER be heartbeat-revived, must re-auth), `status [surface]` (surface's view), `status-raw` (mount state itself).
- Lock trigger per surface — WEB: the library page POSTs `/api/private/lock` the moment navigation leaves private/ (all navigation flows through `navigate()` in app/library/page.tsx); a `pagehide` sendBeacon to `/api/private/lock-beacon` covers tab close. DESKTOP: the lock manager (`vdloader-private-autolock.service`, 3 s interval) releases the desktop lease after 3 consecutive polls with ZERO `/proc` refs (open fds on files under the mount OR cwd inside) — closing the folder window is "navigated away".
- TTL (1800 s) is a pure BACKSTOP for lost sessions/closed tabs — never the primary lock. Tests must backdate lease CONTENT (write an old epoch), not `touch -d` (only mtime changes; the loop reads content).
- Web API reads the lease via `isPrivateUnlockedFor('web')` (`lib/private-vault.ts`; `isPrivateUnlocked()` aliases it so every web write/read gate — downloads POST, fs/list, fs/folders, fs/entries, stream, thumb, folder-zip, downloads/[id] — is web-lease-scoped with zero call-site edits). `isVaultMounted()` = raw mount, diagnostics only, never access control.
- `POST /api/private/lock-beacon` is session-cookie auth with NO CSRF on purpose: beacons cannot send headers and locking is the conservative direction. Never add an unlock path there.
- Unlock with the vault already mounted by the OTHER surface (desktop holds mount, web wants in): the route verifies the password via a throwaway second gocryptfs mount at `/run/user/1000/vdloader/vault-verify` (0700), unmounts it immediately, then grants the web lease. gocryptfs officially supports multiple mounts of one cipher — do not "simplify" this away to mounting the shared mountpoint again (fails `Invalid mountpoint: not empty` once anything exists in the bare dir).
- `vdloader-private-autolock.service` = the lock manager loop: expire stale leases, release desktop lease on zero refs, unmount when no leases live AND no fds hold vault files (streams finishing defer the unmount silently).
- Mountpoint hygiene: gocryptfs refuses to mount over a non-empty bare directory. Anything found in the bare dir while LOCKED is a plaintext-leak stray (written during an unlock/lock race) — inspect, unlock, move it INTO the vault, never delete. Never `mkdir`/write inside the mountpoint path while locked: bare-dir strays then block every subsequent unlock.

## Credentials
- The VAULT password and the app LOGIN password are two different credentials — never interchangeable in either direction. When an unlock or login fails, first confirm which password the surface actually wants.
- **Misdiagnosis trap (2026-09-16 incident, FIXED):** a non-empty bare mountpoint (plaintext strays) makes gocryptfs fail with 'Invalid mountpoint: not empty' and BOTH the web route and private-vault.sh reported it as 'Wrong password' — the user chased a password that was never wrong. Both surfaces now parse gocryptfs stderr: rc 12 + 'Password incorrect' → wrong-password message; 'Invalid mountpoint' → PRIVATE_MOUNT_DIRTY 409 (web) / plaintext-content message (script); anything else → mount-error message. If 'unlock fails with the right password', inspect the bare mountpoint for strays FIRST.
- Stray handling (recovered 2026-09-16): strays under the bare `private/` dir = files written during an unlock→lock race. Stash them OUTSIDE the mountpoint, unlock, move them INTO the vault, then run the backfill script (rows may already exist). Never delete strays, never mkdir inside the bare mountpoint.
- The live vault password is whatever unlocks via kdialog. A KDE Wallet copy (`VDLoader Private Vault`) can go stale — verify any stored copy against the LOCKED vault with `printf '%s' "$PW" | gocryptfs -q -passfile /dev/stdin <cipher> <mnt>` before relying on it. On mismatch, re-save the wallet entry at the desktop; never re-key the vault to match the copy.
- Wrong-password signature: `failed to unlock master key … Password incorrect.`, rc=12. gocryptfs rejects cleanly — a deliberate wrong-password test damages nothing and locks nothing out. The web unlock route rate-limits 6 attempts / 5 min (module scope → per server process) and returns 429 `PRIVATE_RATE_LIMITED` — e2e test suites must wait the window out or they fail every subsequent unlock case spuriously.

## Testing the vault (session-injection pattern)
- Authed API calls without the owner's password: insert a temp row into `sessions` — `expires_at` must be a DATETIME string (`datetime('now','+1 hour')`); epoch ints compare falsely against `datetime('now')` and yield silent 401s. Send `Cookie: vdloader_sid=<id>` + `x-csrf-token: <csrf_token>`, DELETE the row after. Existing harnesses: `~/Work/scratch/vault-lease-e2e.py` (27 lease cases) and `~/Work/scratch/vault-navigate-e2e.py` (11 navigate-away cases) — copy their helpers instead of rewriting auth/plumbing.
- Unlock-route smoke: wrong password → 401 `PRIVATE_UNLOCK_FAILED`; correct → 200 `{ok,unlocked:true}` + lease file exists; lock → 200 + lease gone + (no other lease) mount gone.
- Stream-deferral regression: open an fd on a vault file, backdate the lease, assert raw status stays unlocked, close fd, assert unmount within a few intervals.
- Drain-down tests after unmount transitions: the lock manager only unmounts when refs == 0, so a test shell whose cwd is inside the mount, or an fd left open by a previous assertion, silently blocks the unmount — assert from outside the mount tree and close every probe fd before asserting.

## Desktop prompt-on-navigate (`private-watch.sh` + autostart .desktop)
- inotifywait on the mountpoint pops the kdialog password prompt when the LOCKED folder is opened (2-min throttle, 2-min prompt timeout). Only watch while LOCKED: every mount transition swaps the watched inode, so arm with `inotifywait -t 60` and re-check mountinfo each cycle; ignore timeout exits.
- Launching outside a desktop session requires `WAYLAND_DISPLAY=wayland-0 XDG_RUNTIME_DIR=/run/user/1000` or kdialog cannot reach the display.
- The `Unlock Private Folder.desktop` shortcut lives on the BARE mountpoint: place or verify it only while LOCKED — when unlocked it is covered by the mount and would otherwise land INSIDE the vault (encrypted content).

## Web unlock API
- `GET /api/private/status` → `{unlocked}` (web-lease view) · `POST /api/private/unlock` `{password}` (owner + CSRF; rate limit as above; wrong password → 401) · `POST /api/private/lock` `{}` (releases WEB lease only) · `POST /api/private/lock-beacon` (cookie-auth, lock-only). Passwords reach gocryptfs via 0600 tmpfile deleted immediately — gocryptfs re-opens passfiles by path, so `/dev/stdin` fails when Node owns the pipe; argv would leak to every process list.
- When the vault is already mounted by the OTHER surface, the web unlock verifies the password via a throwaway second gocryptfs mount at `/run/user/1000/vdloader/vault-verify` (0700, unmounted at once) before granting the web lease — re-running gocryptfs against the shared bare mountpoint fails with `Invalid mountpoint: not empty` and would misreport a correct password as wrong.
- Rate limiter note for e2e suites: the 6/5-min counter is module-scope in the unlock route, so a full test run exhausts it — suites must treat 429 as 'wait and retry' (15 s poll) or backdate lease CONTENT instead of replaying unlocks.
- gocryptfs works under the preview service's systemd context — when web unlock fails, probe fuse in a service-like env (`systemd-run --user --unit=<tmp> --wait` calling the helper) to split "environment denies fuse" from "wrong password" before touching code.
- UI surfaces: the library page's `PrivateUnlock` panel (auto-shown when navigating into private while locked; a status poll re-shows it) and the same panel inside FolderPicker. Private folder listings must go through this flow — never render the bare mountpoint's contents.
- Legacy idle-autolock and its busy-detection tests are superseded by the lease model; the fd-leak rule survives: every ReadableStream wrapper over a vault file MUST destroy its fs stream on cancel, or a leaked handle blocks unmount forever (diagnose via `/proc/<pid>/fd` scan).
