**`rounded-[inherit]` silently breaks when you wrap the element:** a ring/mask div styled `rounded-[inherit]` resolves its radius from ITS PARENT, so inserting a positioning wrapper between it and the real radius source makes it fall back to `0px` — the mask then clips to a sharp-cornered rectangle and the effect "ignores the container's border-radius". Symptom reads as a path/geometry bug, so it misdirects debugging into the wrong layer. Any wrapper you add between a `rounded-[inherit]` element and its radius source MUST itself carry `border-radius: inherit`. Verify with `getComputedStyle(ring).borderTopLeftRadius === getComputedStyle(container).borderRadius` — a `0px` on the inner one is the entire bug.

**Glow law (owner order, standing): glows are DARK MODE ONLY.** Every `text-shadow`, every `filter:drop-shadow`, and every colored halo inside a `box-shadow` must be inert under `[data-theme="light"]`; only neutral black elevation shadows survive there (menus still lift off the page). Border/color changes are NOT glows — keep them. Apply as a scripted pass, never hand-edits: rewrite-in-place the light rules that carry their own glows FIRST, then generate overrides for the rest, and compare (selector, prop) TUPLES when skipping hand-tuned light rules. Full parser recipe + the two bugs that cost cycles: `references/decorative-css-batch.md`. Never edit a shared chip class to style one button — add a modifier class (`.chat-chip-options`). **Corollary for icons:** because light mode has no glows at all (rule above), a pale icon cannot be rescued with brightness on paper — give it a SILHOUETTE. A dark outline stroke (`.steer-note`-style `stroke` on the shape) is what keeps a silver moon or an amber sun legible on cream; verify with a close-up capture, not a grep.

**TypeScript narrows a discriminant ACROSS an early return — and `@ts-ignore` was hiding it.** A sidebar view-mode (`mode = 'nav' | 'chats' | 'files'`) rendered panels via `if (mode === 'chats') return <aside>…`. After that return, TS narrows `mode` to `'nav'` for the REST of the function, so a later `item.name === "Chats" ? mode === 'chats' : …` is flagged TS2367 "no overlap" — even though the runtime value is perfectly valid. The repo had been carrying a `@ts-ignore` on that line with a comment claiming it was "strict-mode inference". Adding a second mode reproduced it. Two rules: (1) never silence TS2367 with `@ts-ignore` — read what the narrowing is telling you, it is usually correct; (2) route the comparison through a MODULE-SCOPE helper (`function sidebarModeIs(name: string, mode: string) { … }`) because function parameters are not narrowed at the call site, while local `const`s are. Corollary: when a chained ternary tests the SAME variable twice (`x === 'a' ? … : x === 'b' ? …`), the second test is narrowed by the first — destructure to a lookup or hoist to a helper instead of stacking ignores.

Sister-repo shape/motion techniques (live-verified):
- **Touch-target trap:** the global `@media (pointer:coarse){ button,[role=tab]{min-height/min-width:44px} }` block defeats single-class counters — `.x { min-height:0 }` only ties the bare `button` rule and loses to `[role=tab]` (equal specificity, later rule wins). A compact control's counter-rule must name BOTH `button.x` AND `[role=tab].x`. This was the root cause of "filter pills too tall on phone".
- **An animated border line must BE the path — a straight element travelling a path can never trace a tight corner.** Over an arc of radius `r`, a straight bar of length `L` departs from the path by `r(1-cos(L/2r))`; at `L=170, r=12` that angle is over 7 radians, so the "line" is a chord that flies off the corner. No radius pinning, path override or aspect-ratio tweak fixes this — it is inherent to translating a straight segment. Same trap in a different guise: a `conic-gradient` sweep is angular, and angular degrees cover more physical border near a corner, so it stretches there. **The working implementation is an SVG stroke on a rounded `<rect>` (`src/components/composer-trace.tsx`)** — the dash IS the rounded path, so it is geometry-exact at every point, and it cannot render as a second line. `pathLength={100}` normalises the dash maths so the lit run is a constant share of the perimeter (identical length on every edge) and a `stroke-dashoffset` sweep of `-100` is exactly one lap, which makes the loop seamless. Read the host's REAL `border-radius` at runtime and pull the rect radius in by half the stroke width, or the corners sit proud of the CSS radius. Keep the host's idle `border-color: transparent` so the stroke IS the border. Reduced-motion: `display:none` it (a frozen line reads as broken), never freeze it. **Do not reintroduce a moving-element-on-a-path approach** — it was tried through four rounds (conic gradient → SVG dash → `offsetPath` rect → `aspect-square` bar) and every one of them was wrong at the corners.
- **A ZERO-LENGTH dash is INVISIBLE under `butt` and a DOT under `round` — so the linecap is load-bearing whenever the dash pattern opens with a zero.** The comet bands all begin with the leading `0` that forces the gap on (`0 ${a} ${b-a} ${rest}`, three separate defects traced to that one line). With `stroke-linecap: round`, that zero-length dash renders as a full round dot of the cap's diameter, AT PATH POSITION 0 — for EVERY band, and the brightest band's dot (opacity ~.97) is the one you actually see. Symptom: a stray bright tile/dot at the far end of the comet tail, detached from the line, sitting at a fixed place on the border (the dash origin) rather than travelling with the sweep. It reads as an asset or stray-DOM bug, not a CSS one, so it sends you hunting in the wrong layer. Fix is one value: `butt`. **Prove it by A/B pixel capture, not by reading the dash math** — freeze the animation at one phase (`animationPlayState='paused'` + a fixed negative `animationDelay`), screenshot the SAME corner at 4-8x, then flip only the linecap and re-capture; the dot is present in one and absent in the other. Grepping the dist for `stroke-linecap:round` finds the culprit but does NOT prove it is the thing on screen — and note the flip may have landed in the UNCOMMITTED working tree, so `git diff` against HEAD is what shows who changed it. Corollary: whenever a dash pattern's first value is `0`, keep `butt` and never "prettify" it to `round`.
- **"Entirely inside the bubble" needs the row to be a CHILD of the bubble, not a sibling with a negative margin.** An action row rendered as a sibling and pulled up with `margin-top:-30px` straddles the bubble's bottom border — it is half in the glass, half out — and switching it to `position:absolute` does NOT fix it, because the nearest positioned ancestor is the scroll pane, so the row anchors to the viewport, not the bubble (it then floats in the middle of the feed). Neither CSS-only fix works: the row has to be BUILT INSIDE the bubble element, which means the bubble component needs an `actions?: ReactNode` slot and the parent passes the row down. Two sibling traps follow: (1) each bubble must become its own positioning context (`position:relative`) or the absolute row escapes to the scroll pane; (2) the reserved height is the *docked row's*, so compute it as inset + half the 44px hit area (e.g. `bottom:6px` + `padding-bottom:42px`) — reserving the full 44px leaves a slab of dead space under every bubble. Verify by GEOMETRY on a real conversation with bubbles, not by eye and not on a greppable property: assert `actions.parentElement === bubble` and that the action rect is within the bubble rect on all four sides, in BOTH bubbles. Measure glyph-vs-icon gap separately — the 44px boxes overlap the text's line box by ~8px by design, and only the 16px SVG's `getClientRects()` top vs the last text range's bottom tells you whether anything the eye can see actually collides (~9px clear is right). **Hover-only rows are invisible in a headless capture** — if the run reports `hover:none` (touch emulation) they sit at opacity 1 and you get a lucky screenshot, but on a desktop capture you see nothing and may "confirm" a bug that isn't there; force `style.opacity='1'` before capturing, and assert on the rects rather than trusting the frame either way.
- **A comet gradient on that path must be NON-OVERLAPPING bands, and the head must LEAD.** Three separate defects all presented as the same owner complaint ("a dimmer line runs behind the bright one"), and each looked like a styling nit rather than a maths error: (1) **overlapping translucent strokes COMPOSITE** — alpha at a point is the SUM of every band covering it, so bands sharing a leading edge render as a flat plateau with a cliff at the end, which is literally a bright line with a dim line behind it. Tile the comet with each band painting only its own slice: `stroke-dasharray: 0 ${a} ${b-a} ${100-b}`. (2) **`stroke-dasharray` alternates DASH-then-GAP**, so that pattern NEEDS the leading `0` — without it the pattern opens with a dash of length `a` and band 0 paints most of the border at full brightness (a hard bright plateau). (3) **Orientation:** a clockwise sweep paints band `[a,b)` at `[a+t, b+t)`, so the band's HIGHER path position is the FRONT — the falloff must RISE with band index (peak on the last band) or the comet travels correctly while its glow trails at the back, which reads as the whole thing running backwards. Getting only the `@keyframes` sign right still looks backwards; direction and falloff are two separate facts. Sweep `-100` = clockwise (rightward along the top, then down the right edge); `+100` = anticlockwise. 9s, `linear` (an eased lap pulses speed at the loop seam — the opposite of seamless).
- **Before hand-rolling any decorative UI, search the component registries (owner standing order):** `mcp__magicui__searchRegistryItems`, `mcp__aceternity__search_components`, `mcp__shadcn__*`. Magic UI JSON is public — `curl -s https://magicui.design/r/<name>.json` then read `files[].content` with python (web_extract strips JSX); `mcp__magicui__getRegistryItem` returns name/description/dependencies but NOT the source. Aceternity returns 0 for niche effects (no border-beam equivalent) — a 0-result search is a finding, not a blocker. Vendor components land BYTE-FOR-BYTE; brand values go on the call site props, never in the vendor file. Never target a vendor element with a fragile selector like `[class*="border-transparent"]` — wrap it in a project-owned div and style that. **The same search-first rule covers ICONS and ART ASSETS, not just components** — the owner rejected hand-drawn theme icons outright ("I don't want you to create new icons, search Lottie or any other framework or existing packs"). Icon sets live in a different place from component registries: add `mcp__iconify__search_icons` (indexes hundreds of filled/illustrated sets and returns real SVG paths) alongside the component registries, and check whether an animated-SVG or Lottie pack already ships what you need. Asset sources + gated-CDN drop-zone recipe: `references/icon-assets.md`.
- **When the owner names a reference implementation, port its COMPONENT verbatim — not just its technique.** The standing instruction for the theme toggle was to duplicate comindash's implementation using "the exact same components copied and pasted from there and then modified for our requirement". That means the SVG markup, viewBox, mask structure, stop values and child order come across IDENTICAL; only the layers that must differ get adapted. Porting a technique and inventing new markup is a different, worse deliverable — and it is the port that makes diffing against the reference possible. Same discipline as vendor registries below, different source.
- **Verify visual work with EYES, not greps — and a login wall is not an excuse.** Bundle greps (`grep -o` the served `index-*.css`) prove code SHIPPED, never that it LOOKS right; "dual lines are back" happened repeatedly after grep-verified deploys. For a login-walled app whose secret is on disk, minting a session and actually looking is always available (sister repo: `~/.config/astra-webui/env` → POST `/api/login` on 127.0.0.1:3011 → plant the `astra_session` cookie via `cdp('Network.setCookie')`; recipe in `references/qa-auth.md`). A session cookie is not a password — never type or ask for the password itself. Handing back "I can't verify this visually" when the means were sitting in an env file reads as avoidance, and the owner will call it. If you still cannot verify, say so plainly and name the exact knobs — never open a report with "verified" for a change whose entire claim is appearance.
- **After the SECOND rejected take on a subjective visual parameter, stop tuning and offer choices.** Purely aesthetic knobs (comet length, glow strength, falloff curve) have no correct value discoverable by measuring — an agent looping "measure → adjust → screenshot → measure" burns many rounds and still misses, because the owner's judgement is the spec. The move is to ship the best current state, then present two or three CONCRETE named options ("zero tail: one crisp dash / softer head: drop it to plain brand cyan / softer falloff") with the exact knob each one changes, and let the owner pick. A one-line knob table beats another speculative iteration. Corollary: a terse reply after several rounds ("make the line longer", "just testing") is a signal the loop is not converging — read it as such rather than as the next micro-adjustment. **Corollary that ends the session honestly:** if a fix spree starts stacking failures (a swap animation breaks, then the fallback breaks too), STOP and `git checkout --` back to the last verified-good commit rather than shipping the newest broken state — and say plainly which request went UNDONE. A clean revert plus a named outstanding request beats a half-working feature plus a claim that it is done. Also: when a toggle's icon semantics are ambiguous (icon shows the CURRENT theme vs the theme you'd switch TO), the owner may flip the answer mid-session — ask once, in one line, before implementing, rather than inferring and re-implementing.
- **Recognized slash commands: strip the `/` from the textarea's OWN value — never mirror it.** (The mirror approach was built, then removed: it caused BOTH reported symptoms.) A textarea cannot color a substring, and the tempting fix — `color:transparent` on the textarea plus an absolutely-positioned mirror div in brand blue, with the leading `/` hidden via `<span style="visibility:hidden">/</span>` — is wrong twice over. `visibility:hidden` still occupies the slash's width, so `/steer` renders as `" steer"` (a leading gap); and the native caret lives in the textarea, which still contains the slash, so it sits one character right of the visible text ("typing line is not synced"). Any attempt to paper over the gap with a negative margin just re-breaks caret alignment. **Correct approach:** on recognizing the command, set the textarea's real value to `cmd.slice(1) + remainder` (no slash at all), keep the command in a `cmdPrefix` state, and re-attach it in `send()` (`prefix + " " + value`). Then `.cmd-active { color: brand; caret-color: brand; text-shadow: glow }` styles the real textarea and the caret is correct for free — no overlay, no alignment maths. Clear `cmdPrefix` on send and when the input empties. Corollary: **any overlay drawn on top of a textarea must share its exact text metrics** — compare computed `fontSize`/`lineHeight`/`fontFamily` before touching positioning. The composer placeholder hit this: the iOS zoom guard `@media (hover:none){ textarea{font-size:16px!important} }` bumps the textarea to 16px on every touch device while `.composer-ph-text` stayed 14.5px, so placeholder, typed text and caret were laid out on different metrics on every phone. Any overlay on a textarea must be added to that same media query.

- **/bg vs /steer are different jobs — separate surfaces (owner mandate):** /bg = run-after queue via `prompt.submit {queued:true}`; the dock above the composer is its job tracker — queue-position badges on queued rows, elapsed timer on the running row (item id doubles as createdAt, Date.now mint), reply-jump chevron when done, filter to bg kind only. **A bg turn's REPLY does not paint in the chat feed at all** — tag the assistant bubble with the owning item id (a `bgTurnRef` set on submit, cleared when the turn completes so the next plain chat message paints normally again) and gate rendering through a pure predicate.
