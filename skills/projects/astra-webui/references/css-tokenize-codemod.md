# CSS tokenization codemod (astra-webui)

`scripts/theme/tokenize.mjs` rewrote 785 literals → 295 channel vars with zero visual change (harness-verified). Re-runnable/idempotent; `--reset` restores `index.css.bak`. Rules that transferred:

- **Comment placeholders must carry their own delimiters.** Store `/*...*/` verbatim, substitute a bare marker (`\u0000N\u0000`), restore marker → full comment. Keeping outer `/*` `*/` in the template AND in the stored comment produced `/*/* ... */` — 136 nested openers, lightningcss mis-parsed, and every subsequent rule silently broke.
- **Split definition blocks from consumer rules.** `:root`/`@theme`/token-remap blocks keep their literals (they ARE the defaults); consumer rules get `rgb(var(--c-N)/a)`. Custom-property declarations inside consumers also stay.
- **Role mapping is CONTEXT-AWARE.** Dark rules map dark-palette literals to roles (`#0a0a0f`→void, `#f8fafc`→brandtext…); light rules map light-palette literals. The same literal family in the OPPOSITE context is a hand-picked override (white text on a coloured button in light mode) and keeps its own channel var — mapping it to the role silently re-tints it. This shipped once and was caught only by the light-mode parity states; dark states were clean.
- **Neutral black/white shadows stay literal** (elevation, not theme). Classify shadow parts by chroma; don't tokenize pure neutrals inside `box-shadow`/`mask`.
- **Normalize spelling at compare time, not codemod time**: computed `color(srgb …)` vs `rgba(…)` are the same colour (see visual-parity-harness reference).
- **Theme engine (`src/lib/theme-store.ts`)**: discover channel vars from CSSOM once, override Tailwind `@theme` `--color-*` vars directly for the mode, persist selection in localStorage, re-apply pre-paint in main.tsx. Tailwind utilities reference `var(--color-*)`, so overriding THOSE re-tints utility classes; channel vars alone only re-tint literal consumers (a `text-brandtext` heading ignores channel vars entirely — this gap showed up live as "palette changed: false" until fixed).
- **Palette transport**: HUE-based role mapping over base16 YAML — slot semantics drift per scheme (tokyo-night-dark base08 is a fg tint, not red). Score accent candidates by hue family (teal/blue/violet bonus) + saturation; terminal themes are identified by their blue/cyan/violet. Base16 YAML parses with a 20-line flat parser — full PyYAML is unnecessary. Verify generated identity colours against each theme's known look (Laya verify_claim) before shipping. Base16 YAML writes slots lower-case (`base0a`); normalize keys to upper-case ONCE at parse end instead of sprinkling per-access fixes — a partial upper-casing pass is how slot KeyError loops start.

## Runtime re-palette: retarget EVERY derived var, not just exact-default matches

The first engine rewrote only vars whose default triple EQUALLED a canonical token triple — gradient bottoms (`#0891b2`), dim glows and other precomputed shades of the accent kept astra blue forever. Two-part structural fix:

- **Annotate roles in CSS, and keep the channel prop's FULL name in the annotation.** tokenize.mjs emits `--r-<channelProp minus leading dashes>: <role>` beside each role channel var (`--c-66` → `--r-c-66`, `--light-c-33` → `--r-light-c-33`); the runtime builds `chanProp → role` from CSSOM with `"--" + prop.replace("--r-", "")`. Two silent-failure traps, both shipped once: (a) a bare `--` prefix yields `--66`, which never matches the channel prop `--c-66`; (b) **stripping the `light-` prefix collides with an unrelated `--c-N`** — `--light-c-33`'s annotation was written as `--r-33` while no `--c-33` exists, orphaning the role for 34 light props, which then fell through to accent-scaling instead of using the palette's own light colour. After ANY tokenize change, assert zero orphans: every `--r-*` must have a `--(light-)?c-*` prop with an identical suffix (`--r-light-c-26` ↔ `--light-c-26`).
- **Never restore `src/index.css` from the codemod's `.bak` on this shared repo.** The `.bak` is a snapshot from one tokenize run; concurrent sessions keep editing `index.css`, so restoring it silently reverts everything added after that snapshot — one restore deleted a whole feature batch and failed 21 CSS checks while looking like a clean "regenerate". Recover with `git checkout -- src/index.css` and patch the live file in place. Related: `tokenize.mjs` is idempotent and DETECTS ITS OWN OUTPUT — re-running it on an already-tokenized file prints `already tokenized; nothing to do`, so you cannot regenerate from the current file; the pristine source is HEAD, never the stale `.bak`.
- **Iterate channel props directly, never a triple-keyed lookup.** Dozens of vars share the default triple `34 211 238`; a Map keyed by triple keeps only the LAST one, so all but one glow stayed astra blue. Walk the rule list, collect every `--(light-)?c-N` prop + default, then per prop: role → palette colour; untagged accent-family shade → `deriveShade()` (scale each channel by new-accent/old-accent, clamp 0–255) so gradient bottoms and dim glows keep their relationship to the new accent.
- **Event-listener order at boot:** register sync/push listeners BEFORE `restorePalette()` — the restore broadcasts `astra-palette-change`, and a broadcast fired before its listener exists reaches nothing (the cross-device push silently never fired).
- **Prefer `color-mix()` at USE time over precomputed shade vars** for anything that must track the accent (send/new-chat gradients, bubble bg/border/glow): `linear-gradient(var(--color-cyanx), color-mix(in oklab, var(--color-cyanx) 62%, var(--color-void)))` re-tints itself on every theme and in light mode; precomputed shade channel vars are what went near-invisible on pale accents. Same for the bubble surfaces: `color-mix(in oklab, var(--color-cyanx) 7%, transparent)` bg, `30%` border, `35%` halo; user bubble same on emerald — one rule per surface, every theme, both modes.

## Mode switch: the toggle path and the boot path must produce IDENTICAL state

The owner's report "switching dark→light doesn't port over, I have to reload" is a DIVERGENCE between two calls of the same function: `applyPalette()` run at runtime by the toggle, versus run at boot on a fresh load. Reproduce it as an A/B diff, never by eyeballing which surfaces "look wrong":

- **Diff the two states directly.** Dump `getComputedStyle(document.documentElement)` for EVERY custom property plus the inline `style.getPropertyValue` set, plus a list of surface computed styles, in both the toggled and the fresh-reload state; diff them and report the count. The fresh-reload page IS the correct answer — it is the reference implementation.
- **Diff the WRITES, not just the values.** Monkey-patch `CSSStyleDeclaration.prototype.setProperty` before the action and log `[prop, value]` in both paths. The value diff shows the symptom; the write diff localizes it to a branch.
- **Run the whole matrix**: desktop toggle, mobile toggle (open the drawer first), and the DEFAULT palette — each against its own fresh-reload control. The default theme is a separate code path and diverges independently.
- **Track the count** (224 → 0 this pass). "Some surfaces repainted" is not a pass; a partial fix reads as success until you count.

Four root causes this exposed, all real:

1. **Channel triples were stored comma-joined (`"15,23,42"`) while `channels()` and the accent guard used spaces.** So `rgbKey !== astraAccentCh` was ALWAYS true — every prop took the derived-shade branch, including the accent itself — and `deriveShade()` split the comma string into ONE token, producing `NaN NaN NaN` channels. Pick one delimiter for every store/read/compare site; accept both at the boundary with `split(/[\s,]+/)` and validate `Number.isFinite` before writing.
2. **The `astraAccentCh` guard compared only the CURRENT mode's accent.** A prop holding the light accent was accent-scaled when the palette was applied in dark mode but skipped in light mode — same prop, two answers depending on which mode it was applied in. Compare against BOTH modes' accents.
3. **`astra-ui` IS the stylesheet default.** `:root` holds its dark values and `[data-theme="light"]` its light ones, and boot deliberately skips it. The toggle wrote 280 inline overrides for it where boot wrote 5 — the paths disagreed by construction. When the selected palette is the default, CLEAR our inline overrides and return; let the cascade supply the values.
4. **Non-colour palette tokens were never applied.** `--glow-accent`, `--glow-accent-strong`, `--bg-url`, `--bg-video` differ per MODE (dark defines a glow, light sets `none`), so skipping them left dark-mode glows burning on light paper after a toggle. Write them verbatim alongside the `--color-*` ones.

**`--light-c-N` and `--c-N` are INDEPENDENT props with their own colours and roles.** The light scope's `--light-c-4` is paper while `--c-4` is cyanx. Do NOT "fix" an unroled prop by aliasing its role from the non-light twin — that is the obvious-looking fix and it turned the composer solid dark blue on the toggle path (the prop then resolved to the accent instead of paper). Only the prop's own `--r-*` annotation is authoritative; props the tokenizer left unroled are deliberately theme-stable own-channel literals.

**A value that happens to equal a palette role colour is NOT a role.** The tokenizer only tags literals it can resolve in the scope they appear in, so an unroled prop holding a role colour (a light literal in a dark-scoped rule) tempts a `roleByTriple` fallback map. Don't add one — it mis-maps across modes and reintroduces exactly the divergence you are fixing.

Deploy check: the role annotations live in the CSS (grep the SERVED `index-*.css` for `--r-light-c-`), the runtime fixes in the SERVED JS. Verify both from the served bundle, never `src/`.

## Palette generator + WCAG audit (build-palette.mjs + a11y-pass.mjs)

- **Audit TEXT tokens, not just accents.** The first a11y pass only checked accents ≥3:1; brandtext/muted pairs at 1.0–4.4:1 shipped through it. The pass must step lightness on ANY failing pair (text and muted to ≥4.5:1, accents to ≥3:1) and re-run to convergence — one pass can create a new failure, so loop until "fixed 0".
- **Light-origin schemes need a synthesized dark variant.** For a scheme whose BASE00 is paper (tokyo-night-light, solarized-light, rose-pine-dawn), the naive inverted order yields a LIGHT void with light text (contrast 1.0–1.5). Force it: darken the void until `lum <= 0.09`, then set text to `adjustL(darkVoid, 0.78)` and muted to a ≥4.5:1 step — never trust slot order to produce a dark ground.
- **Light variants: void and brandtext came from the SAME slot** (BASE01) — literal contrast 1.0. Paper takes the lightest surface; ink must be a genuinely darker slot or a synthesized `adjustL(lightVoid, -0.72)`, asserted with a real contrast check, not slot identity.
- **Astra UI is the untouched-canonical invariant:** after every regeneration + audit, assert its dark/light tokens still equal the shipped values (muted dark was the one sanctioned change, 4.09→4.70:1). If a regeneration moves astra-ui, the generator changed under you — fix the generator, not the output.
- **Distinct light papers need an IDENTITY TINT, not a lightness push.** Deriving every scheme's light void by `adjustL`-ing its lightest slot toward white collapses them all to one near-identical off-white (`adjustL` preserves hue+sat, and at L≈0.96 with tiny sat every scheme lands within 2 RGB steps of the same grey) — the owner reads that as "the light themes are all pretty much the same". Fix: blend the scheme's paper hue with the CIRCULAR MEAN of its accent-slot hues (~70% accent weight), set saturation to a real tint (10–20%, scaled by the accents' own saturation), and vary lightness by hue warmth (warm hues lighter ~0.945, cool deeper ~0.935). Each light theme then reads as "that theme, in daylight" the way its dark sibling does. Verify by grouping all light voids by hex — duplicate groups are the failure signal.
- **New palettes ship as YAML additions to the generator's SOURCES map** (fetch from tinted-theming/schemes spec-0.11), then the pipeline is: build-palette → a11y-pass → build-palette → a11y-pass (loop until the audit reports zero fixes) → assert the astra-ui invariant. The generator's tiny YAML parser already strips trailing `# comment` values; a preview script that forgets the comments reports every slot as missing — test the real parser, not a lookalike.
