## Notifications cannot be themed CARDS — only made theme-AWARE (verified 2026-10-03, commit 835c619)

Notification layer = `NtfyPushService.kt` (channels `astra-push-v2` approvals / `astra-chat-v2` replies / `astra-connection` foreground status) + `GateActivity.kt` (full-screen approval popup).

**THE CEILING, not negotiable:** since **targetSdk 31** (Android 12) an app cannot draw a fully custom notification layout — `setCustomContentView`/`setCustomBigContentView` are wrapped in a standard system template, and `createBigContentView` is **deprecated in API 35** ("no longer required to be used directly by the System UI"). At `targetSdk 36` the OS renders every card itself, so a notification whose BACKGROUND follows the palette is **not achievable**. The app controls only accent colour, small icon, title/text, style family, grouping, actions. Never promise the owner a themed notification card — the reachable surface is accent + icon + the GateActivity popup (our own View tree, fully restylable). The only route to themed cards is a full-screen overlay Activity per notification, which hijacks the lock screen.

**`NotificationChannel` has NO colour setter.** `javap` on android-36 shows only `setLightColor` (the LED). There is no channel tint to retheme, and delete-then-recreate only resets the user's own importance/sound/badge choices — never do it on a theme change. Channel accent comes from the per-notification `Builder.setColor`, which IS the correct lever. In Kotlin `setColor` on a channel is an unresolved reference: it does not exist and is not a property.

**The theme→native bridge that now exists (do not build a second one):**
- `src/native/shell-theme.ts` → `pushThemeToNative()` resolves the ACTIVE palette from **live computed styles** (`getPropertyValue('--color-cyanx')` etc.), so custom token edits count and not just `palettes.json`. Pushes 10 tokens + `mode`; fires on `astra-theme-change`, `astra-palette-change`, a boot `setTimeout(300)` and a 5s change-gated tick (signature-compared, so the ticker is free). That file already owned `AstraBars.setBackgroundColor` (window decor) and `Preferences astra_theme` (GateActivity light/dark) — those three are the whole native theming surface.
- `AstraThemePlugin.java` (`@CapacitorPlugin(name = "AstraTheme")`, registered in `MainActivity.onCreate`) → `sync({mode, tokens})` normalises `#rgb`/`#rrggbb` BEFORE writing (a malformed hex is dropped so only that token falls back to Astra), commits tokens + `astra_theme_stamp` in one write, then starts the service with `ACTION_THEME_CHANGED`. **Java calling a Kotlin `object` needs `AstraThemeRead.INSTANCE.invalidate()`** — a bare call does not compile.
- `AstraThemeRead.kt` reads `CapacitorStorage` and caches against the stamp (notifications build in bursts; per-notification disk reads are waste). `AstraTokenMath.kt` is **deliberately free of android imports** — `android.graphics.Color` is a stub in JVM unit tests, so every pure function lives there and is testable without a device. `AstraTokenMathTest.kt` is the runnable check (11 asserts, all passing).
- Live repaint: `ACTION_THEME_CHANGED` → `repaintChats()` re-issues each posted card from retained `ChatState` via the extracted `chatNotification(state)` (no network, no re-resolve) + `updateGroupSummary()` + `publishStatus()`. Gate cards are deliberately NOT resurrected — one-shot payload + actions, and the user may have dismissed them. `ChatState` carries `sid` for exactly this reason (the delete-intent and `ACTION_CHAT_CLEARED` key on it).
- Android's `Color.parseColor` reads **#AARRGGBB** while CSS writes **#rrggbbaa**. Mixing them swaps channels silently — build an alpha colour with `Color.argb`, never by appending alpha to a CSS hex.

**Text ON an accent: pick by measured contrast, never by a luminance threshold.** A mid-luminance accent breaks a threshold — Fire `#FF5C1F` (lum 0.29) takes **dark** text at 6.39:1 while white gives only **3.09:1**. `onAccent()` takes the max of the two measured ratios. Found by the unit test, not by eye.

**Build:** `assembleDebug` fails at `packageDebug` with `SigningConfig "debug" is missing required property "storePassword"` unless you `set -a; source ~/Work/services/astra-android/astra.keystore.env; set +a` first. Confirm new native classes actually shipped — `unzip` the APK and `strings` the `classes*.dex`; a green build does not prove a class is inside.

**Live-fire part 2 (found while writing the verification report): the on-device test needs BOTH halves and they shipped in different places.** The APK carries the native plugin/resolver, but it loads `https://astra.jitinnair.com` LIVE (`stripBundledWebAssets` runs inside every assembleDebug — the app never ships a bundled dist), so `pushThemeToNative()` in `shell-theme.ts` executes only from a DEPLOYED site build. Handing over the APK without redeploying the site leaves the bridge silent. Emulator remains invalid for this path anyway (host AVD ships WebView 133 < 140).

Repro once both halves are live: install APK → let a chat reply land → flip dark/light in the app → the accent repaints in place. Silent = debug from the phone's logcat, not this host.

## Pitfalls
- **On Astra surfaces, a multi-step status/analysis answer renders as a canvas card, never a prose blob.** Skill-review/audit answers (what's loaded, what's stale, what ops ran) are exactly the use case for `astra-canvas` blocks (kpi row + table + callout). - **Research deliverables on this surface ship as canvas CARDS plus prose with inline `[n]` + a ## Sources block (proven shape, 2026-10-04).** 11 canvases across 4 research answers: kpi+quote+danger-callout+compare / callout+steps+table+flow-diagram / diagram+steps+limits-table+checklist+warn(refined to done|open|fail)+references / `graph` consumer map with `kind:"asserted"` dashed edges + evidence table + checked-absent checklist. Two rules that matter beyond that reference:
- **A `code` block containing ``` needs a FOUR-backtick fence, or the card renders as raw text.** The closer must be longer than any backtick run inside the body, and the canonical demo for this feature is itself a fence regex — so this fires on the most obvious example. A three-backtick fence closes inside the JSON, the body is cut mid-string, and the whole card degrades while the parser looks healthy. Parser-side, `scanFences` probes candidate closers and takes the first whose BODY PARSES; strict line anchoring looks correct and silently breaks real cards. - **Canvas parsing is TURN-level, never per-segment.** A tool call, message boundary or non-extending `text-final` splits one assistant message across several text segments, and a fence crossing that boundary is unparseable in both halves — it degrades to a code block and reads as "canvas missing from mid responses". `planTurnCanvases` stitches the turn's segments, parses the whole, and classifies each fence: CONTAINED fences stay inline in the markdown (so prose after a card stays below it), only SPANNING fences are extracted and anchored to the segment where they close. - **A canvas renders IN REAL TIME, block by block — never wait for the closing fence.** `parseStreamingBlocks` walks the partial JSON brace-by-brace (string/escape aware) and validates each top-level `blocks` element the moment its brace closes, so `CanvasView` paints a `partial` spec with a "Building…" indicator while the model is still streaming. Pitfall: the brace walk must track strings — a `}` or `{` inside a `body`/`code` value ends an element early and silently drops blocks.
- **A canvas degrades PER BLOCK, not whole-card.** `parseCanvasSpec` keeps every block that validates and returns null only when NONE do; `lenientJson` strips `//` / `/* */` comments and trailing commas first; `validateBlock` accepts near-miss type names (`metric`/`stat`→kpi, `plot`→chart, `flowchart`/`flow`/`map`→diagram, `list`/`todo`→checklist, `note`/`warning`/`insight`→callout, `meter`/`bar`/`gauge`→progress, `sources`/`citations`/`links`→references, `snippet`→code) and chart kinds (`donut`/`doughnut`→pie, `columns`→bar, `gauge`→radial). `graph` is NOT in that list — it is a real block type now, and the old `graph: "chart"` alias silently hijacked it (aliases resolve BEFORE `BLOCK_TYPES`). - **A NUL byte in a source file makes BOTH grep and ripgrep skip it silently — and "0 matches" reads exactly like "the code isn't there."** `chat-timeline.tsx` joins memoized markdown blocks with a literal `"\0"` separator, so every content search over it returned `total_count: 0` while a directory listing still showed it. A recursive `grep -rn` reports only `binary file matches`, giving zero lines and no hint that anything was skipped. Suspect this the moment a targeted search returns nothing for a symbol you have personally seen in the file: confirm the file is not being treated as binary (`grep -c $'\0' <file>`), then re-run with `-a` (or `--text`) to search its contents as text. Never conclude a call site is absent from a search that skipped the file.
- **A comment above a timer is not a guard — read the body.** "1 Hz while a retry is pending" sat above an interval whose callback had no such condition, so a `setNextRetryIn` fired once a second for the app's whole life and, because `hermes-ws.ts` subscribes to that field and nothing is memoized, re-rendered the 2,005-line chat component every second while idle. When auditing timers, verify the CONDITION in the body; the comment is where the bug hides.
- **A `useEffect` whose dep array includes the state its own poll callback writes re-arms its own interval** on every reconciliation — the 3 s `session.resume` poll in chat-landing depends on `bgItems`, which `reconcileWithServer` rewrites. Symptoms look like "the network is busy"; the timer is just never allowed to settle.
- **`assets/public/` in a `server.url` Capacitor app is dead weight AND a latent trap.** The WebView never reads the bundled copy, so it is pure APK bloat; and a bundle that predates the last `dist/` build will silently shadow the live site the moment anyone flips `server.url` off. Prove which case you are in by comparing mtimes, not by reading the config.
- **Dex file count in the APK is the R8 tell.** 8 `classes*.dex` for ~2k lines of your own Kotlin means `minifyEnabled false`; check the base file too — `proguard-android.txt` is not `proguard-android-optimize.txt`. - **A prod dependency with zero importers is install-time cost, not bundle cost** — it is tree-shaken out. Report it as build hygiene and supply-chain surface, never as a bundle win; verify with an importer grep rather than inferring from the dependency list.
- **A storage prune sweep that covers one key prefix leaves its siblings growing forever.** The daily `pruneStaleBgItems` sweep only matches `bg_items_`, so the per-session draft keys and the per-backdrop video-position keys written by the same features accumulated without bound. - **Two durable queues for one concern is a trap for the next editor.** `outbox.ts` was a fully-built, well-commented, capped durable queue that nothing imported, while `ws-store.ts` carried the live one under a different key. Grep importers before trusting a queue's existence.

- **A NEW `*.check.*` file turns the repo gate RED until it is pinned in the manifest.** `scripts/regression-gate.check.mjs` greps `src server scripts` for `*.check.*` and fails any file absent from its `REGRESSIONS` array — “add a row or it is unpinned”.
