# Strangler-fig Rust port (parity-gated)

## When to Use

Rebuilding a Python codebase in Rust (or another fast language) while the original stays the running, untouched spec — file-by-file, parity-gated. Any port where "behaves identically or better" must be proven by execution, not assertion. Also covers the supporting arc disciplines: corpus audits of hand-rolled parsers, research-before-arc plan docs, and smoke-before-install service rollout.

Canonical instance: the Taal project (`~/Work/taal`, Hermes→Rust).

## Standing rule: port by hand

Hand-port; do not delegate the porting to subagents or other models — the owner mandated planning, porting, and testing all done by the primary agent. Delegated builds under-port large scopes (stub-level output with self-authored happy-path tests, three-for-three observed) and their "tests pass" claims hide skipped semantics. Adjacent chores (dependency research, environment prep) may delegate; the port itself and its test runs never.

## The loop (one reference file per cycle)

1. Pick the next file in dependency order (leaf utilities first, entry points last; two god-files never adjacent). Read it COMPLETELY — every branch, threshold, counter, ladder — plus the area's AGENTS.md.
   For god-files (3K+ lines), do NOT port top-to-bottom: layer them internally and gate each layer as its own ledger row — (a) the pure core (classification helpers, constants, format gates) first, (b) orchestration glue as trait seams (the trait exposes exactly the attributes the reference reads), (c) the machinery (locks, threads, DB, executor) last. Earlier layers' traits become the contract the later layers implement, so nothing ports twice. When reading one class inside a multi-class god-file, extract it with an awk range (`awk '/^class X/,0' file`) and work in class-relative line numbers — absolute line numbers against a mid-file class mis-target sed windows and you keep re-reading the wrong region.
2. Port it. Same semantics, Rust idioms. Keep every doc-comment's WHY. Carry invariants structurally where possible. Build new modules as several small single-purpose files (one function group each) with a `cargo build` between them — single giant file writes corrupt mid-write (placeholders like `fn x() -> { todo!() }` appear mid-file), and small units localize the damage. After any long file write, grep it for `PLACEHOLDER`/`placeholder`/`todo!()` before compiling — mid-write corruption announces itself as stray markers, and a compile pass can still leave a silently-truncated tail. When a file still corrupts, do NOT rewrite the whole file: append intact sections with `cat >> file << 'EOF'` heredocs and repair the damaged span with targeted patches — a full rewrite re-rolls the corruption dice.
3. Gate it: unit tests + a cross-language parity check + one adversarial check you invent yourself + a mutation check of the new suite (break the port a few targeted ways; every break must turn the comparator red) + a corpus audit when the module parses real-world inputs. **If the reference ships tests for this module, replay them** — a pytest plugin that traces calls into the ported functions turns them into parity rows, and it finds bugs your own golden structurally cannot (in one session it surfaced a mis-transcribed constant, a branch that only fires when a dict has no nested key, a helper implementing one of four message grammars, and a whole classification stage never ported, all while the module's hand-written suite had been green for sessions). Recipe in the `rust-verification-harnesses` skill under `reference-test-replay`.
4. Check dependencies: every caller/callee of the ported module in the reference tree, config/env/files it reads. Note wiring in the ledger.
5. Record a ledger row (file → target → state → exact evidence: command + output) and extend the structural-audit symbol map for the new file in the same commit. Audit keys are real reference file paths — one entry per file, with a multi-layer god-file port merging both layers' symbols into that single entry (a suffixed key like `file.py::L2` fails the reference-exists check). Verify the edit landed by the audit's printed file/mapping count, not by the patch script exiting 0 — the same silent `str.replace` no-op that hits source files hits the audit map, and a missing entry surfaces sessions later as a coverage mismatch. Only then COMPLETE.
6. Drive through ALL planned layers/phases of a file or arc in one session without pausing between them for confirmation — the owner wants whole-file completion momentum, not per-phase check-ins; report honestly at the end, including exactly what remains. Never land a stub for safety machinery (compressors, leases, fences): a stub passes CI and corrupts sessions silently — if time runs out, the honest open item beats a fake green.

## Gates

- **Line-count sanity**: a faithful port lands at 60–110% of the reference's line count (tests included). Below ~40% = skipped semantics — reject and redo.
- **Never accept "tests pass" alone**: run the suite yourself, then add one adversarial input the author never wrote. Proven catches: a mid-JSON SSE chunk split behind 12/12 green; CRLF + YAML block scalars behind 54/54 + 17-section parity (197/512 real files mis-parsed).
- **Hand-written goldens cap out below the reference's own test suite — and the gap is invisible until you measure it.** Coverage percentage is the cheap first look: instrument with `cargo llvm-cov -p <crate> --all-targets` (never `--lib` alone — parity runners are separate binaries, so every runner-driven module reads 0% and looks like dead code), then read the report's SECOND `Cover` column for line coverage. Before declaring a module fully covered, ask what fraction of the reference's own tests for it you replay; the reference is the only place where its real bug history is enumerated.
- **Mutation-check every new suite before trusting it** — apply targeted breaks to the port (drop a marker, invert a guard, skip a heal), rebuild, and require the comparator to fail on each; restore the original in a `finally`, and assert each mutation anchor is unique so a refactor turns the check noisy instead of silently skipping it. A SURVIVOR is usually a fixture gap, not a strong port — fix the scenario to cover the behaviour and re-run (proven shapes: an ordering rule whose fixtures never contained both orderings; a method that reads the shared map raw while every scenario loaded it first). Only then classify what genuinely cannot be killed as documented-equivalent, with the reason printed by the check — never silently dropped. **Before calling a survivor a fixture gap, rule out that the MUTANT is broken instead**: an edit that changes nothing survives by construction (`let _ = &t;` after an existing `return`; `.trunc() as i64` → `as i64`, since Rust's `as i64` on `f64` already truncates; a boolean flag short-circuited by `&& false`). Prove it by applying the mutant by hand and reading the comparator — an identical diff to the survivor means the mutant is a no-op, so delete it and replace it with one that changes an entire `if` / `let (target, other)` construct rather than nudging a literal. Two proven shapes: a branch that needs the reference's threads; and an arm dead in THIS module because the owning caller lives elsewhere (a clear-flag unreachable behind the skip guard that reads it) — verify that against the reference before classifying, never by assuming.
- **Transcribe POLICY CONSTANT TABLES and canonical marker strings from the reference source, then confirm them in the golden** — a plausible-looking table (image limits, cooldown ladders, char caps, threshold minimums) is wrong more often than right when written from memory or a docstring summary; the reference module's own constants block is the only source. Include every named constant in the parity golden's `constants` section so the table itself is diffed, not just behavior downstream of it. The same rule covers marker/canonical-text builders (prune markers, status lines): print the reference's exact output with `repr()` and paste that, because a paraphrased marker parses differently. For LONG byte-pinned text (multi-paragraph prompt sections, wire-prefix screeds, historical-prefix tables), skip transcription entirely — write a generator script that imports the live reference module and emits the Rust `const` file (`json.dumps` per string), commit both; hand-copied paragraphs drift on a stray apostrophe, and only a full-string parity row catches it.
- **Corpus-audit hand-rolled parsers against the real data they will parse** — synthetic fixtures reflect what the porter imagined; the live corpus contains CRLF files, `>`/`|` block scalars, list-of-maps, nested frames. Harness: reference dumps per-file parsed fields for every real input → Rust bin replays → diff names/descriptions/bodies/conditions. Cheap to build, catches the class of bug nothing else can.
- **Measure which reference LINES the golden executes, scoped to the functions you actually ported.** `parity/refcov.py <gen> <ref.py>[:func,Class.method]` traces the generator with `sys.settrace` and reports executed vs executable lines plus the UNEXECUTED lines with their source. Scope the function list when a file is layered — an unscoped run reads low because the layers you have not ported yet cannot execute, and the number stops meaning anything. The unexecuted list is the real prize: it names the `except` arms, `mkdir` calls and attribute writes a happy-path fixture never reaches, and each becomes one more golden section. Treat 100% over the claimed functions as the gate; whole-file coverage only once the whole file is ported.
- **done-decision gate before claiming complete**: verify claims against the commands actually run — and run the full campaign AFTER the ledger/audit edits and the commit, not before; evidence gathered before the last edit proves the wrong tree and reads stale to the gate. "After the last edit" includes doc/handoff edits: a suite count quoted after any later file change is unverified. Numbers quoted in commit messages and completion claims come from output that has ALREADY printed — never from a total you expect the pending run to produce. When the gate returns `partial`, it is naming missing evidence — produce exactly that evidence and re-run the gate; do not re-argue the claim.

## Parity harness layout

- `parity/gen_<area>_golden.py` — runs the PYTHON reference, writes golden JSON
- `crates/<crate>/src/bin/<area>_parity_run.rs` — runs the RUST port on the same fixtures, writes answers JSON
- `parity/compare_<area>.py` — diffs golden vs answers, exits nonzero on failure

Run all three; a green compare is the file's gate. For how to WRITE the generator — choosing fixtures from the reference's own tests, pinning clocks/filesystems/loggers, and turning refcov's unexecuted lines into rows — see `references/golden-generator-recipe.md`.

### Live-state replay parity (runtime-dependent pipelines)

Static fixtures cannot exercise code paths that merge RUNTIME state — plugin/tool registries, live availability probes, env-derived schema text. When the owner asks for real-world validation (or the pipeline merges such state), ALSO build a live replay harness alongside the static one: the Python side dumps the real runtime object graph to portable JSON (entries plus RECORDED probe verdicts, so the Rust side needs no Python handlers), and a Rust bin replays the dump through the ported pipeline. Keep BOTH suites green — static proves module logic on pinned inputs, live proves the merge paths on the actual deployed state; neither substitutes for the other. Rules:
- **Install the replay registry into the port's process-global seam before selection** — without it, every registry-merge branch (plugin toolsets, alias unions) is dead code under test, static fixtures pass, and the live path ships unverified.
- Compare env-dependent text (descriptions embedding install state, live-generated docs) by SHAPE (names/params/presence), not bytes; keep byte-compare for port-owned logic only.
- Generate the golden through the assembly-skipped path when that seam belongs to a later row, and record the delta (tools the live side defers behind a bridge, dynamic rewrites it applies) as comparator rows explicitly marked seam-off/informational — they quantify future-layer headroom and must not fail parity.
- Pin a fresh registry in STATIC goldens (swap the module-level singleton for an empty one) so they test the module's own logic, not the dev machine's plugin set.

When the reference file is mixin glue over a mutable `self` (no pure return value), port it as a trait + free orchestrator fn: the trait exposes exactly the attributes the reference reads, defaults mirroring its `getattr(x, k, default)` fallbacks; the god-file implements the trait when it later ports. Python's `result is input` no-op detection becomes an explicit `same_list: bool` in the return tuple (Rust cannot compare Vec identity). Pin the **contract matrix** instead of bytes: script every combination of the input flags (pins, ownership, outcome classes), run both sides, and diff WHICH side-effects fired (error stamps, telemetry writes, rollbacks) plus the caller-visible result/error class. Record the ORDERED dependency call log too — a fake DB/service that appends every call with its args catches wrong-order and missing/extra-call bugs that the result diff alone cannot. Record the reference's error-class mappings in the comparator (e.g. a stale-attempt guard that unwinds via the cancellation exception must map to the same error class, not a distinct one).

- **Port the reference's ALGORITHM for policy/helper functions, not a plausible reimplementation from the docstring** — walk its actual code (prefix sums, floor semantics, quanta) and port statement by statement. A reimplemented "equivalent" agrees on the cases you imagined and diverges on boundary inputs (byte-vs-block overshoot, floor sheltering). Verify by running the REFERENCE on your exact fixture rows and recording its numeric answers into the golden — expected outputs come from execution, not from reasoning about the docstring.
- Golden/runner authoring rules (each cost a debugging session) — see `references/golden-generator-recipe.md` for the generator recipe, and keep these when writing the RUNNER side:

- Set mock attributes explicitly — one named assignment per line, names copied from the reference source — never `MagicMock(**{...})` from a dict literal. A mistyped key doesn't fail: MagicMock auto-creates a child Mock, `isinstance(x, (int, float))` goes False, and the golden silently encodes behavior the reference never had. `MagicMock(spec=SomeMixin)` is the same trap inverted — spec strips private attributes, so `_underscore` reads raise AttributeError; use a plain MagicMock. When a golden value surprises you, print `type(mock.attr)` first — a `MagicMock` type means an attribute-name typo. And when the reference TYPE-PINS its reads (`x is True`, `isinstance(x, int) and not isinstance(x, bool)`), drive the golden with a plain hand-built object carrying explicitly-set attributes — a Mock's auto-attribute machinery fails the pin closed and the golden silently records the fallback path instead of the real value.
- Drive golden fixtures through the reference's REAL entry points — constructors, property setters, public methods — never by assigning private `_resolved_*`/cached fields to shortcut deferred initialization. A private-field shortcut skips derived-state recomputation (a `context_length` setter can re-derive the threshold percent from the window), so the golden bakes in a state the production path never produces; the mismatch then indicts a correct port, and "fixing" the port toward the golden number corrupts it. When a golden number disagrees with a direct source-reading of the math, suspect the fixture's entry path before the port.
- Define each fixture ONCE in the runner and derive everything (anchors, grown histories) from that variable; duplicate literals between golden and runner are the top cause of FALSE parity failures. Golden-side shape/observation helpers must read marker keys and sentinels THROUGH the reference module's exported constants (`m.get(cc._COMPACTION_TAIL_MARKER)`), never a hand-typed string — the hand-typed key silently reads absent and flattens every row to False, and the missing flag reads as a port bug in the diff.
- When a reference method signals success by RETURNING None, record `r is None` in the golden — a `bool(r)` wrapper encodes every success as False, and the port then "fails" parity on rows it handles correctly. When fingerprints or hashes disagree, dump the hashed input from BOTH sides and diff it before suspecting the algorithm. And reset or reconstruct reference state between golden rows — a mutated attribute leaking from fixture N into N+1 poisons the golden itself, and a CORRECT port then fails parity chasing a phantom bug; when the Python side of a diff looks semantically wrong (an iterative-update form where a fresh one was requested), suspect the golden generator before the port.
- Normalize Python's `{}`-as-empty return against Rust's `None` in the comparator (treat `{} == null` as equal) or every empty-sentinel case fails. Same for `""` — Python functions that return a falsy `""` (not `None`) must port to the exact same shape; check the reference's return statement, not Rust idiom. Sets are the trap twice over: a golden that records a bare Python set/frozenset serializes its `str()` repr (`{'a', 'b'}`), which equals no Rust shape ever — emit `sorted(list(...))` from the generator and sort the Rust collection to match. A trailing comma after a golden assignment (`OUT["x"] = fn(...),`) records a TUPLE — the comparator then reports a type diff (`[False]` vs `False`) that indicts a correct port; when a bare boolean shows up as a one-element list, grep the generator for a trailing comma on that row.
- Keep byte-level fixture literals identical across languages (`"x" * 4000` vs `"x".repeat(4000)`; trailing spaces survive). A hand-shortened copy of a long literal drifts and the diff points at the wrong function.
- The runner must execute mutations and observations in the SAME order as the golden — batching mutations upfront and checking afterwards produces false mismatches whenever a read is order-dependent (ownership, generation counters, current-owner checks). Mirror the golden's sequence statement by statement. The inverse bites too: a Python golden recording results inside a dict-literal or spread evaluates those expressions at the END of the sequence — capture the Rust observations after all mutations (or re-read live state at record time), never into locals mid-way. And when a golden field is named for the assertion but stores the raw return (`"stale_refused"` holding `clear()`'s False), apply the negation in the golden itself — otherwise the comparator diff indicts the port for behavior that matches.

## Porting pitfalls (measured)

- **`serde_json::json!` hits the macro recursion limit on wide literals (~45+ entries in one expression) — "recursion limit reached while expanding `$crate::json_internal!`".** Build big objects programmatically: a `Vec<(&str, String, String, String)>` of rows plus an insert loop into a `Map`, never one giant `json!({...})`.
- **Two crates' binaries with the same name collide in target/release — last build wins.** Name every runner `<area>_parity_run`; a bare `parity_run` silently executes another crate's binary and errors on that crate's fixtures.
- **Python `read_text`/`open` apply universal newlines (CRLF→LF); Rust `read_to_string` does not.** Normalize `\r\n` at every ported-parser entry or CRLF-authored files diverge.
- **Hand-rolled YAML subsets aren't done until block scalars (`>`, `|`, `>-`, `|-`) and list-of-maps work** — a large fraction of real-world frontmatter uses one of these.
- **The `regex` crate has NO lookahead** — reference patterns with `(?!...)` need an equivalent two-step (match the superset, then exclude in code).
- **`concat!` needs literals** — pattern tables built from shared `const` fragments must become runtime `String` concatenation inside a `OnceLock` initializer.
- **Never route Rust string literals containing `\"` through a Python heredoc patch** — the escape is consumed twice. Write fix scripts to scratch files and run them; never inline nested-quote code. Shell variables do NOT interpolate inside a quoted `<<'EOF'` heredoc — `{VAR}` reaches Python as a NameError; pass values as argv or environment and read `os.environ`.
- **Patch scripts that mutate source via `str.replace` fail SILENTLY when the anchor string doesn't match** — `assert anchor in s` before every replace and verify a count/contents check after; a no-op replace leaves the file unchanged while the script prints "patched", surfacing sessions later as a ledger/audit count mismatch. Same rule for any generated edit: verify the edit landed, not just that the script ran.
- **Generated registry files (audit maps, symbol tables) verify by content, not by the edit script's exit code** — entries appended AFTER an early `sys.exit(main())` never execute, so an audit can stay green for sessions while a dead tail of entries goes unchecked; and a restructuring that replaces whole keys silently drops their mappings. After any edit: the printed file/mapping count must match expectation AND the old-vs-new key sets must diff clean for losses.
- **A parity-cleanup `git checkout -- parity/` wipes UNCOMMITTED audit/ledger edits made earlier in the session** — the checkout exists to reset regenerated parity answers, but it discards any audit-map or ledger edit not yet committed (proven twice: entire row batches' audit entries vanished, and the audit kept passing green on reduced coverage). Scope the cleanup to `parity/answers_*.json` only, and commit audit/ledger edits in their own commit immediately after verifying the printed count — never carry them uncommitted across a parity run.
- Python `json.dumps` default separators are `", "` / `": "` — serde_json compact drifts. Mirror the format exactly for anything byte-compared.
- **Python estimators that hash or measure `str(value)` measure the dict REPR** — single quotes, `True`/`False`/`None`, insertion order. Port a `py_str_of`/`py_repr` pair or every estimate drifts low; when two fingerprints disagree, dump the pre-hash string from both sides and diff it before suspecting the algorithm. The same repr rule applies to any `str()`/`_content_text` helper that stringifies non-string values: a dict becomes `{'k': 1}` (single quotes), not JSON; list-part text joins use the reference's own separator (often `"\n"`, sometimes `""`) — read it, don't guess.
- **When a parity fix changes a canonical shape (marker text, constant, format), stale unit tests fail AFTER the commit** — settle each against a fresh reference run of the exact fixture, then fix the expectation; do not weaken the parity-verified port to match old tests.
- **`find | xargs wc -l | tail -1` undercounts large trees** — xargs splits into multiple invocations, each printing its own `total` line, so `tail -1` reads only the last batch. Any number a plan or estimate relies on comes from a single-process per-file line sum, never a piped `wc` total.
- Provider-report structs need `#[serde(default)]` on every field; env-mutating unit tests serialize on a shared Mutex (cargo runs tests in parallel threads).
- **Any test touching a process-global (registry, OnceLock cache, env var) holds one shared lock for its WHOLE body** — not around individual calls. A sibling's `clear()` landing mid-test corrupts register→apply→assert sequences and presents as a 1-in-10 flake in an unrelated assertion. Guard every global-touching test in the module, not just the ones that mutate.
- **Flake-capture loops belong in a script file run in the background, logging each run's summary to a file** — a `for` loop inline in a foreground tool call hits approval timeouts and dies with the evidence. Loop `cargo test --no-fail-fast` writing full output to a capture file on the first failure; a flake that stops reproducing before capture leaves nothing to fix from. Expect to need 10–30 runs for a 1-in-10 flake.
- **Python `RLock` is re-entrant; Rust `Mutex` is not** — a reference method that calls another method which re-locks the same guard deadlocks silently in the port (presents as a hung test, not an error). Inside a locked section, read the already-held state directly instead of calling a helper that re-locks, and enforce enter/exit boundaries with an RAII guard so the discipline is structural. In tests, never invoke the blocking variant of a method while one of its guards is live in the same thread — assert through the non-blocking/try variant, which is what the reference's single-threaded probes effectively do.
- **Port Python background-daemon threads (heartbeats, lease refreshers, watchdogs) as tick-driven state machines, not threads** — the run-loop body becomes `tick(&mut self, observed) -> Option<Action>` called by the executor layer, with suppression latches, failure-streak tolerances, and interval math transcribed unchanged. Tests drive ticks deterministically instead of sleeping, and the detached-zombie failure class (a timed-out worker's late `stop()` republishing state the host already owns) is impossible by construction. Keep the touch/emit side effects as an action enum returned from the tick — the port stays pure and the executor owns I/O.
- Trait-method ambiguity: when a super-trait graph has two same-named methods with defaults, qualify cross-trait call sites (`DriverAgent::method(agent)`).
- Port Python truthiness explicitly (`bool([])`/`bool({})` are False); transcribe numeric constants from the reference source, never from memory. String-ladder classification is the same trap amplified: when the reference classifies content by prefix sets, exact-string sets, or marker regexes, READ the definition in the reference source — never invent a plausible marker shape or prefix — and when in doubt run a probe in the reference venv that prints the real constants and the classifier's verdict on your fixture content (a set-membership check and a prefix check agree on every test string you'd guess and differ on the ones you wouldn't).
- **Config/settings-parser ports must replicate Python's RAW-value coercion, not typed accessors** — a reference `bool(section.get("enabled"))` treats the string `"yes"` as True, and `float("5")` parses to 5.0, while Rust `.as_bool()`/`.as_f64()` return None for string-typed values and the parser silently keeps the default. Parse numbers out of strings and coerce truthiness over every JSON shape (empty string false, non-empty true) before applying defaults.
- **A port with a process-global singleton seam (registry, plugin host, cache) tests the merge path ONLY when the seam is installed** — parity fixtures that leave the seam `None` keep every registry-merge branch (plugin toolsets, alias unions) untested while everything else goes green. Wire the real or replay implementation into the seam for at least one harness before calling the module complete.
- **When a reference helper builds a set/map over message fields, port WHICH COLLECTION it iterates, not just the field name.** A sanitizer's `result_call_ids` is the ids of RESULTS PRESENT (iterated over tool rows), not the ids of declared calls — inverting the iteration direction keeps every well-paired transcript correct and only diverges on the orphan cases the function exists for. For each union-building loop, name the loop variable after the collection it walks before writing the Rust version.
- **When a reference loop rebuilds a formatted value (marker, message) inside its iterations and consumes it after the loop, the value USED is the in-loop one — port the loop structure verbatim, not the post-loop intent.** Rebuilding the marker after the loop from the final computed count changes output bytes; a 'stale-by-one-pass' value is the reference's contract, and only a byte-exact parity row reveals which variant the reference actually emits.
- **A reference with several token/size estimators has call-site-specific contracts — port the one each call site actually uses.** Budget walks may charge `content + fixed overhead + tool-call envelopes` while preflight estimators charge the whole wire-shadow repr; the two differ by formula and by ~10 tokens per row, so porting the wrong one onto a boundary walk shifts every cut it computes. Grep the call sites of the function you are porting to identify its estimator, and unit-check one fixture row's token count against a live reference probe before trusting any walk derived from it.
- **Background process logs go stale when a newer process lands — re-list by mtime before reading output.** Several false dead-ends per session are stale-log reads, not real failures.
- **Before accepting an arc, grep the port tree for SAME-NAMED functions across crates** — a "shadow" variant carrying the same name as the parity-verified one, zero call sites, and a comment asserting the reference "collapses into" it is unjustified drift: the next porter greps, finds the wrong one first, and builds on it. Delete the shadow or make it delegate to the verified implementation. A tell: a boolean parameter feeding a no-op (`.max(if flag { 0 } else { 0 })`) means the flag is silently ignored — the signature promises semantics the body does not deliver.
- When a test fails, re-read the reference for the exact semantics before touching port or test — wrong expectations are as common as port bugs.
- **Validation lives where the reference puts it** — when a Python constructor returns a partially-populated record (`None` fields) and a separate `_serialize` rejects it, keep the invalid state representable in the port and reject at the same boundary; rejecting at construction changes what callers observe.
- **Byte-format test expectations come from a live reference run, not from reading the f-string** — run a one-liner that prints `repr()` of the reference's output lines and paste those exact strings into the Rust test; eyeballed padding and mark placement are wrong more often than right. The same holds for POSITION and OUTCOME expectations: when a ported function inserts at an index, merges, or takes a branch ladder, run the reference on the exact fixture and record where things land — the rule that fires first (e.g. a boundary scan before an append fallback) is easy to misread from source.
- **Code that reads global config can't be tested through args alone** — tree walkers read the real home directory first; point the config seam (an absolute-path create-dir or external-dirs entry passes through untouched) at a temp tree and use unique names so the real tree can't shadow the fixture.
- **Capture a transient test failure in the run that shows it** — but first confirm it reproduces on a clean re-run AND check for concurrent CPU competitors (a local Ollama serving a graphify pass, a parallel cargo build, another session's test run): a first run showing 2 failures that goes 0-failures on three re-runs is CPU contention, not a bug. Then, for a real flake, immediately re-run with `--no-fail-fast`, writing the full output to a file. A flake that stops reproducing leaves no evidence to fix from; report it as open, never as silently green.
- On resuming a multi-session port, `git log` is the ground truth — handoff docs and their HEAD references lag the last commit. Run the verification suite and reconcile the real HEAD first; build on neither the doc's state nor its row list without checking.
- **Modified `parity/answers_*.json` / `golden_*.json` on disk are regenerated ARTIFACTS, never work-in-progress.** A finished campaign leaves them dirty whenever recorded output carries a volatile value: a temp-dir random suffix in a path column, today's date inside a date-stamp string, a per-call hashed filename. Read the diff to confirm the signature before touching them — a real port change never lives in an answers file. Do NOT `git checkout -- parity/` to tidy them either: that wipes uncommitted audit/ledger edits made earlier in the session. Leave them dirty or commit them deliberately. Before writing a fix for a parity failure you remember from an earlier session, re-run that suite and `git log -- <file>` — a sibling session may have already fixed it, and your patch will apply cleanly onto the fixed file and misattribute the divergence (a clean apply proves nothing about which tree you derived it from). While reconciling, fix ledger row order and stale campaign totals — concurrent sessions append rows out of sequence and the ledger is the audit trail.
- **Exception-classifying ports need isinstance-EXACT type matching** — match the qualified type name exactly (`json.decoder.JSONDecodeError`, not `contains("JSONDecodeError")`), because the reference's `isinstance(e, RuntimeError)` is false for any other exception whose message merely resembles it.
- **Port an `Any`-typed guard's non-dict branch as classifying the VALUE itself** — a reference helper shaped `isinstance(x, dict) ? by_message(x) : by_content(x)` passes the bare string/list straight into the content classifier; a Rust `.get("content")` on the non-object silently reads Null and inverts the branch. Match the dispatch shape, not the field name you assume it reads.
- **`serde_json::json!` arguments must be expressions — statement blocks do not parse as macro input.** Hoist computations into named locals (`let preview: String = …;`) and reference them inside `json!({…})`; a `{ let x = …; Value::String(x) }` block inline in the macro fails to expand with an error pointing at the wrong line. Mirror this in the golden: drive exception rows with REAL subclasses (raise/catch a genuine `json.JSONDecodeError`, subclass `RuntimeError`/`ConnectionError` directly) — a duck-typed stand-in with a `type_name` field fails the reference's isinstance checks and silently records fallback-path behavior, producing false mismatches that indict a correct port.
- **A boundary fixture must ISOLATE the behaviour, or it cannot kill the mutant.** Rows that sit below the OTHER threshold in the same comparison never exercise it: two utterances whose `SequenceMatcher` ratio is 0.93 test nothing about a guard at 0.95, with or without the guard in place. Before writing a boundary fixture, compute whether the isolating input is even constructible — one changed character in an `n`-char string caps the ratio at `(n-1)/n`, so a "must differ yet stay similar" pair cannot clear 0.95 below `n = 20`, and if the guard sits at 16 no both-sides-short pair can isolate it. Find the shape where the guard ALONE decides (e.g. 16-vs-15: the minimum length is 15 and the ratio clears 0.95), and prove the ratio with the reference before writing the row.
- **Python `len(str)` counts CODE POINTS; Rust `.len()` counts BYTES.** A `>= N` character guard ported with `.len()` silently mis-fires on astral text (emoji, CJK ext-B) and never mis-fires on ASCII-only fixtures. Use `.chars().count()` wherever a reference `len()` fed a comparison.
- **Port Python's `int(x)` coercion, not `as_i64()`.** `int()` truncates toward zero (`1.5` → `1`), accepts bools as 1/0, and parses numeric strings with surrounding space; serde's `as_i64()` returns None for every one of those, so the port silently takes its fallback arm. Integer-only fixtures never expose it — the coercion rows must be in the golden.
- **An unguarded attribute read in the reference is an ERROR arm, not a `None`.** `raw.guild.id` on an object with no `id` raises AttributeError; a port returning None matches every well-formed fixture and quietly changes the error path. Give it its own result arm and pin it in the golden.
- **A golden generator's stdout must stay pure JSON.** The campaign pipes it straight into `golden_<area>.json`, so one diagnostic `print()` corrupts the file and the runner dies parsing it. Route progress to stderr.
- **Call reference methods through a BOUND instance in a golden, never the unbound class.** `Cls.method(obj, a, b)` passes `obj` as `self` and drops a positional argument, surfacing as a confusing `TypeError: missing 1 required positional argument`. Check `inspect.signature` rather than counting arguments off the source.
- **Make a golden byte-reproducible — no volatile values in recorded output.** A temp-dir path inside a captured warning string leaves `git status` dirty on every run, so a changed path can never be told apart from a behaviour change. Substitute a `<TMP>`-style placeholder.
- **`Vec<String>.contains(&"lit")` fails to compile against owned-string vectors — the element is `&String`, not `&&str`.** In test assertions over resolved/derived string lists use `.iter().any(|t| t == "lit")` uniformly; it fits both owned and borrowed elements and the `contains` variant only surfaces at test-compile time, after you have already moved on.
- **A runner fixture that pre-coerces a wire value makes the port's coercion rows unreachable.** The first voice L1 runner read `guild_id.as_i64()` before calling the port, so float/bool/numeric-string coercion rows never reached `py_int_of` — every coercion mutant passed. Pass the raw `&Value` through and let the port do the coercion; the golden's coercion ladder (`1.5→1`, `True→1`, `"  7  "→7`) is only exercised if the runner hands over what the golden recorded.
- **A parity harness that rebuilds its OWN fake world can silently disagree with the golden's scenario.** Two classes proven on row 67 LAYER 2: (a) a tool_calls fixture built as a FLAT array `["1","function",{...}]` instead of a list of call OBJECTS made the dedup scan read a string and 33 matrix rows inverted; (b) a `delivery_served` flag left at its default `false` in one section silently discarded the whole `voice.auto_tts` fallback arm (9 rows) instead of failing loudly. When a matrix section diverges, group the failing rows by their full scenario tuple FIRST — the count pattern (all of one messages-shape, all of one mode) localizes the runner bug to one fixture branch in a single step.
- **A seam's return value is not proof that a downstream step ran.** A "persist writes an empty payload" mutant survived a whole mutation run because the runner derived `on_disk` from the LIVE voice-mode map instead of recording what the host actually wrote. If a fixture asserts a side effect, RECORD the effect at the seam (a `&mut self` recording method) and assert the recording — never re-derive it from state the port also owns.
- **A seam that only READS takes `&self`; one that RECORDS needs `&mut self`** — and that signature change must propagate through the trait AND every test host. The compiler finding every site is the point; do not weaken the recording to keep `&self`.
- **A golden section that is a single OBJECT is not an array** — `.and_then(Value::as_array)` silently returns None and the block is skipped with no error (a whole section "missing from rust answers" with the code visibly present). Match the golden's top-level shape; log when a known section key fails its shape test.
- **Normalise environment- and run-volatile strings in the COMPARATOR, never by pinning them in the golden.** Two proven shapes: `sys.executable` interpolated into an install hint (machine-specific path → normalize to `<PY>`), and `build_auto_tts_output_path`'s per-call uuid stem `tts_reply_<12hex>.<ext>` (different every run → normalize the stem but KEEP the extension and directory compared — the extension is the opus/mp3 contract). Also compare Python-set-shaped fields (`{p for p in {audio_path, *paths}}`) as SETS — the iteration order is arbitrary on both sides, so sorting either one bakes a coin flip into the fixture.
- **A sync adapter probe is not an awaited call.** `adapter.is_in_voice_channel(g)` is read as an attribute inside a boolean guard, so the golden's call log records only awaited adapter calls; logging the probe as a call row invented a phantom ordering diff on every leave scenario. Before logging a seam call in the parity runner, check how the reference invokes it.
- **A golden must record ALL reference log levels a scenario exercises.** The reference logs the STT suppression at INFO (`logger.info("Suppressing duplicate voice transcript…")`); routing INFO to a no-op lambda made the fixture assert `suppressed_logged: 0` — the absence of a log line the reference always writes. Patch `RV.logger` with the real module-global replacement (NOT `logger.warning = cap` — `Logger.warning` is a C-level slot, instance assignment silently doesn't stick) and give every level the scenario can produce a real collector.
- **A scenario control knob must be popped from kwargs before building the fake.** `voice_channel_api=False` as an adapter kwarg either raised (unknown attribute) or was silently ignored — it is a scenario switch, not an adapter attribute, and the row that meant to test "the API is absent" was actually testing nothing.

## God-file layering (when one file needs multiple sessions)

When a god-file's layers span more than one session, split each layer as its OWN parity-gated ledger row and commit — P2a-state / P2b-text / P2b-driver each carried their own suite. Within one session, drive through all planned blocks of a file without pausing (momentum rule above); across sessions, one row per block keeps every partial state verifiable. The module-tail/public-API of a file is ALSO its own row — the last ~200 lines of exported helpers are easy to skip after the driver lands, and "95% covered" hides exactly the consumer surface the next arc calls into.

## Mutation-loop discipline

A mutation check is a SOURCE-EDITING background job: it snapshots the file, writes a mutant, rebuilds, and restores in a `finally`. That makes it hostile to concurrent edits, and its failure modes impersonate port bugs.

- **Never edit a source file while a mutation loop is running.** The restore overwrites your edit silently — a `mod tests` block you just added simply vanishes, and nothing errors. Ship a small `parity/check_mutation_anchors.py` that asserts every anchor appears EXACTLY ONCE in the port, and run it BEFORE each mutation check and after any interrupted one. Its report is the diagnosis: an anchor at `x0` means a stranded mutant is sitting in the tree, not a bad anchor.
- **Never `git stash` / `git checkout` / snapshot a source file a running mutation loop owns.** An edit loses to the loop's restore and vanishes; a STASH is worse, because it captures whatever the file held at that instant — typically a half-applied mutant — and replays it onto a clean tree AFTER the loop exits, reintroducing a mutant the finished gate never saw. Proof it happened: the loop reports its gate PASS with `fails=0`, the stash reopens as a one-line diff against HEAD, and that diff IS a mutant (a dropped log call, a `&& false`). Diff against HEAD and READ the hunk before believing any `M <source>.rs` you did not write — `git status --short` alone says "modified" and reads as stale WIP. Recovery is `git checkout -- <file>` plus `check_mutation_anchors.py`.
- **Never run two mutation loops against one file.** A foreground loop orphaned by a tool timeout keeps running and fights the new background one; the loser restores a stale snapshot and strands a mutant. List `ps -eo pid,cmd | grep mutation_check` before launching, and kill by PID — `pkill -f mutation_check` matches your own shell command and reports a false "still running".
- **When a file is ported in LAYERS, the mutation lists must partition by target file.** The LAYER-2 list's first run died twice on `anchor x0` because two of its mutants targeted symbols (`apply_voice_mode_enabled`, `toggle_adapter_auto_tts_set`) that live in the LAYER-1 file — the L1 script's snapshot/restore races any other writer. Move such mutants into the layer list that owns the file, and leave a NOTE in the list saying which L1 mutants already cover them. Extend `check_mutation_anchors.py` to walk EVERY (script, target) pair, not one hardcoded pair — its final line must show `anchors=N drifted=0` for each list.
- **Rebuild before reading parity after ANY mutation run.** The runner binary is the last mutant's build, so a stale binary emits a diff byte-identical to the surviving mutant's — which reads as a port bug and sends you editing correct code. Signature: one unrelated section failing with a value that is obviously the mutant's.
- **Budget the wall clock from the mutant count, not the gate count.** Each mutant is one full release rebuild of the crate, so a suite's mutation gate dominates a campaign. Quote the measured campaign time in the handoff and schedule against it.
- **When a long campaign is already running and you were asked only to REPORT, poll it read-only and let it finish.** The gate is the evidence you are about to quote; stopping it or editing its files converts a green run into no run. `ps -eo pid,cmd | grep -E 'mutation_check|run_campaign'` plus a tail of the log is the whole job — the campaign writes its own sentinel line (`CAMPAIGN fails=0`, `CAMPAIGN_EXIT=0`) and prints the per-gate PASS/FAIL as it goes, so you can report from the log while it is still running. Use long foreground sleeps between polls rather than tight loops; a poll loop that outlives your turn keeps a tool call alive for no benefit.
- **A survivor is diagnosed, not accommodated — and the honest diagnosis takes three shapes.** Proven in one run (36/42): (1) a NO-OP mutant (`.trunc() as i64` → `as i64` is identical in Rust; a guard whose write-back is separately guarded) → delete it and record WHY it is equivalent; (2) a BROKEN mutant that doesn't compile (a replacement dropping its `;`) → fix the replacement; (3) a REAL fixture gap → add a scenario the golden derived from the reference, not from reasoning. Removing broken/no-op mutants keeps the gate honest — a survivor left in the list trains the next reader to ignore red.
- **A boundary fixture must be constructible at all before you write it.** The 16-char fuzzy guard could NOT be isolated by any both-sides-under-16 pair — one substitution in n chars caps SequenceMatcher's ratio at (n-1)/n, so below n=20 the ratio never reaches 0.95 and the fuzzy arm is unreachable either way. The isolating shape is 16-vs-15 (min length 15, ratio 0.9677): compute the arithmetic FIRST, probe the reference with the exact pair, then write the row.
- **Fixture shapes the mutation check found twice**: a case whose clock advance is too short to expire the entry it claims to expire (the pruned-window write was never observable — the third step must land PAST the window: `6.0 + 6.5`, not `6.0 + 0.5`), and a scenario list with MIXED tuple shapes (`(advance, text)` in one entry, `(text, advance)` in the rest) that only surfaces as a `TypeError` mid-generator. Fix the shape at the definition, not the unpacking at the caller.

## Stopping on request mid-campaign

When the owner says stop while a side-effecting background job is running (a full campaign, a mutation loop that edits source files): send SIGINT, not SIGKILL — the script's cleanup block restores mutated source; then verify the tree before reporting. Verify: every deliberate-mutation anchor holds the original text, no temp files remain, and `git status` shows only expected changes. Never start a new build while a mutation loop may hold a mutated file — you would compile a mutant and "verify" broken code. Report honestly from that verified state: what is committed, what is on disk uncommitted, what was never run.

## Verification cadence within a session

A full-suite campaign after EVERY block is too slow; a campaign only at the end is too late to attribute a break. The working cadence: crate-scoped tests + the new suite after each block (fast, localizes failures), then ONE full workspace + all-parity + clippy + slop campaign before the commit that closes the arc or row. Quote suite numbers in the ledger row and commit message from output that has ALREADY printed (the done-gate rule) — and after any doc/ledger edit, the counts from the earlier run are stale for claim purposes; re-run the affected suite before quoting it as final evidence. Before committing a many-file change, re-read `git status` for files the tree needs that are not staged — `git add Cargo.toml` at the root does not stage `crates/<c>/Cargo.toml`, and a commit whose tree cannot build from clean is worse than no commit. An `--amend` changes the hash: re-point any hash already written into docs, or the handoff dangles.

## Review sessions: report before fixing

### Completion-status review (derive from code audit trail, not prose docs)

When the owner asks "how complete is the port, code only, no docs": the ledger
and audit ARE the code-side source of truth — handoffs/SCOPE prose lag by whole
sessions. Procedure:

1. `ps -eo pid,cmd | grep -E 'mutation_check|run_campaign'` FIRST — an active
   campaign means the ledger tail is in flight: report those rows as
   in-progress, never complete, and never touch the tree (poll read-only per
   the Mutation-loop discipline rules).
2. `git log --oneline -15` — latest row commits carry per-row state newer than
   any doc.
3. Regex-extract the numbered ledger table (`PORT-STATUS.md`):
   `^\|\s*(\d+)\s*\|(.+?)\|(.+?)\|(.+?)\|$` for rows/status; parse in Python
   (execute_code), not by eye.
4. `python3 parity/audit_symbols.py` — quote the LIVE printed counts (files /
   mappings), not a doc's captured tail of the same numbers.
5. Per-area remaining-work figures come from a fresh per-area rglob line-sum
   script (exclude tests), never from stale SCOPE numbers — see the piped-`wc`
   undercount rule above. Write scripts to scratch and run them with an explicit
   `cwd=` (or absolute paths): the execute_code kernel's cwd is the agent's
   scratch cache, not the repo — a relative `read_text` there raises
   FileNotFoundError and costs a dead call before the fix.
6. **Percent-from-ledger arithmetic has two proven traps, both land in one
   session:** (a) scraping any parenthesized number as a line count — `(14.0.0)`
   is a version, `(512)` may be a column width; filter candidates, sanity-check
   the few largest parses by eye against the actual row text. (b) a regex over
   multi-file row summaries captures a big number out of a sentence ("~1,400 ref
   lines" riding beside unrelated tokens) and bonds it to the wrong area. When
   in doubt, quote the ledger's own tally row + the audit's printed file count
   and name the one unmeasured remainder, rather than publishing a summed
   percentage built from partial parses.

Build sessions drive through layers without pausing (rule 6 above). AUDIT/review requests invert that: when the owner asks for a status, divergence, or completion review, diagnose each divergence to root cause, classify it justified vs unjustified with reference-source evidence, and report BEFORE changing anything — "make no changes yet" means the owner decides which fixes run. Never present a fix as already applied during a review; list it as a recommended action and wait. The same discipline applies mid-review when a parity suite fails: run the golden/compare to reproduce, THEN read the reference source for the exact contract (e.g. two-field always-replayed list vs two newest-turn-only fields gated by a flag) before classifying the divergence — the misclassification, not the code, is what a review must never get wrong.

## Driver-level parity (composing phases into a loop)

Per-file fixtures stop proving the wiring at the entry point. Gate the DRIVER with scripted full-agent turns: state copy-back on early exits, trait-method shadowing, and channel-placement of synthetic rows were all composition bugs caught only after 20/20 phase parity. The same rule extends to any MULTI-FILE selection/assembly pipeline: when one function consumes another module's output (selection → registry filtering → schema rewrites), parity the COMPOSED result, not each stage in isolation — a stage can pass alone while feeding its consumer the wrong shape (registry toolset tags alone don't add a tool to the static toolset view; the composed definitions call is what proves membership).

Pin the seam inputs explicitly and IDENTICALLY on both sides — construct the reference object, then override every config knob (`protect_first_n`, budgets, counts) with the same literals the Rust runner passes, because reference defaults drift from the fixture intent (a default head-protection of 3 vs the runner's 1 shifts the whole cut). Compare message SHAPE (roles, marker flags, carrier positions), not full bytes, when the LLM seam is faked — pin `summarize_window`/`_summarize_window` on both sides to the same canned string or None so the diff isolates the driver's own logic. Rust runners passing trait-seam structs (`&dyn Fn` fields) cannot build them inside a closure that returns the struct — the borrows outlive the closure frame; hoist the no-op closures to module-level `fn`s and pass `&fn_name`, or build the struct inline at each call site.

## Static-table ports (toolsets, catalogs, config schemas)

When the reference file is mostly a static dict/list table plus thin resolution logic over it, generate the parity golden from the WHOLE table (every entry's description/tools/includes/extras) rather than sampled entries — a sampled golden passes while a mis-transcribed entry hides in the unsampled majority. Two shape rules from the reference side: extras like `posture`/`role` ride as pass-through keys (serialize them as null when absent so the comparator diffs their presence, not just their value), and any golden that reads a dict whose values are Python sets or the table itself must emit SORTED LISTS — a set's `str()` repr never matches a Rust shape and turns into a phantom type-diff. Resolution rows to always include: a includes-chain entry, the biggest union bundle, `all`/wildcard, and an unknown name (which must resolve empty, not error).

## Research → plan docs before big arcs

Before a multi-session arc (compression, memory subsystem, tools selection), do a cited research pass (arXiv, GitHub, vendor engineering docs, practitioner threads) and write RESEARCH-<topic>.md in the repo: what the reference does, what the field does (with the benchmark numbers that define headroom), the optimization layers, the bench protocol that decides defaults, and the security threats specific to that layer (e.g. prompt-injection via crafted tool DOCS hijacking retrieval+selection — any layer that indexes third-party descriptions must screen them before indexing). Owner decisions get their own decisions doc. Optimizations layer ON TOP of parity and earn their defaults only through the bench (e.g. ≥25% token cut at ≤2pp quality delta, or ≥10pp recall gain for selection layers). Provider-native equivalents (a vendor's built-in tool-search or similar) are an auto-disable path for the custom layer, not a competitor to fight — record when to yield to them.

For a full-codebase port, survey the ENTIRE reference tree before planning arcs (single-process line count per area, not a piped `wc`): separate portable logic from content/dev-tooling dirs that will never port, list the god-files with sizes, and write a SCOPE doc with dependency-ordered arcs that front-loads the shortest path to a live deployable. Point the handoff doc at it — early scope estimates that measured only one area understate the work by multiples and misorder the plan. Size figures carried in plan or handoff docs are stale by default: re-measure the file before scoping an arc (a handoff's "33K god-file" measured 594).

When mapping the port repo with graphify, write `.graphifyignore` FIRST — exclude the reference fork, `target/`, model weights, generated parity JSON (`golden_*`/`answers_*`), and top-level markdown (HANDOFF/PORT-STATUS/PROCESS/SCOPE). Without it the graph is mostly reference Python (wrong language, wrong codebase — thousands of foreign nodes), and the markdown files get dispatched to semantic extraction and fail the run wholesale.

After mapping, VERIFY the project's wiring into the contextual-memory stack rather than assuming it — three separate systems, three separate failure modes. (a) Code graph: the graphify discovery watcher sweeps new project dirs best-effort, but nightly freshness is only guaranteed by an explicit entry in the refresh script's MAPS list — add the project path there so the merged graph served to all harnesses stays current. (b) Doc-level memory: OpenViking ingests nothing automatically; the project's plan/ledger/protocol docs must be explicitly added or they are unreachable via the viking store. (c) Cross-harness agent memory (agentmemory fleet plugin) is a service that must be running — probe its port, not its config. When the owner asks "is this wired into memory", audit all three by query (search the master graph for crate-rooted source files, search viking for the project name), never by config inspection alone.

## Session handoffs

When a session ends mid-port (or an owner asks for a continuation prompt), write the handoff per `references/handoff-docs.md` — one copy-pasteable doc, saved as a committed HANDOFF.md in the repo, carrying rules, verified-state, the cold-runnable suite, and the next queue.

## Deployment notes (when the arc includes a binary)

- Smoke the binary foreground on a test port and drive the FULL wire contract from a client script BEFORE installing the systemd unit; kill the hand-started instance before enabling (same port → AddrInUse, exit 101, reads as a broken unit while the orphan lives).
- Expose new services on a NEW hostname; repoint the live one only from a different surface. Secrets go in a 0600 EnvironmentFile, never in the repo or a bare env var in the unit.
- Live-mode flips need a REAL end-to-end proof before declaring done: send an actual request through the public endpoint and verify a genuine model reply (e.g. an arithmetic question answered correctly + a multi-turn fact recall), not just a health check.
- For a backend-only service whose real frontend lands in a later arc, serve a minimal throwaway test page inline at `/` (single HTML string served by the binary, driving the service's own wire contract — WS JSON-RPC, session create/send). The owner can then test from a phone with zero tooling. Mark it "throwaway — replaced at cutover" in the commit; delete when the real UI lands.
- Test through the path the CLIENT actually listens on, not just the path you can script. A service that both pushes replies over an event channel AND returns them in the RPC response will look fully working to an RPC probe while event-listening clients see nothing — a channel created with its receiver dropped (`let (tx, _rx) = mpsc::channel(...)`) makes every `try_send` fail silently. Render both paths in the smoke page (event frames + RPC result) until the event plumbing is properly wired in its owning arc, and note the dropped-receiver defect in the commit so it is not forgotten.
- **Never describe a test URL from memory during a status report — curl the exact route first.** A backend serving only `/healthz` and `/ws` has no page at `/`; telling the owner "open the URL and chat" sends them to a 404 and costs a trust round-trip. Verify what each route returns (status code + body shape) before naming any URL as user-testable; if the human-facing page doesn't exist yet, say so and offer to add one.
- **A first cargo-test run with 1–2 failures followed by clean re-runs is CPU contention, not a bug** — check for concurrent competitors (an Ollama serving a graphify extraction, a parallel cargo build, another session's suite) before triaging. Re-run to a stable result and quote the stable number, never the contended one.
